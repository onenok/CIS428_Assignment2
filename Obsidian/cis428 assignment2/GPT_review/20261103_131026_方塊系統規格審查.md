- [方塊系統重構設計](../design/方塊系統重構設計.md)
- [方塊系統實作規格書](../design/方塊系統實作規格書.md)

## 結論

目前不建議直接從階段 1 開始實作。應先增加：

> Phase 0：規格修訂與相容性/API Spike

完成 Phase 0 後，才建議從階段 1：`VoxelShape` + `blockShapes` 開始。

## 必須先修正的問題

### 1. DDA 的 shape 座標系統不完整 — Critical

`VoxelShape.boxes` 使用 voxel-local 座標，但規格沒有完整定義 `testRayAgainstShape()` 如何處理 cell/world 座標轉換。

必須補充：

- ray origin 如何轉為 cell-local
- hit position 如何轉回 world 座標
- 非原點 cell 的測試

### 2. DDA 沒有跨 chunk 的 world voxel accessor — Critical

規格只傳入單一 `VoxelVolume`，但建造系統使用多個 chunk，尚未定義：

- world cell 與 chunk/local 座標的轉換
- DDA 如何跨 chunk
- 未載入 chunk 如何處理
- 射線是否限制於可編輯區域

建議新增：

```ts
interface VoxelRaycastWorld {
  getBlock(x: number, y: number, z: number): number;
  shapeFor(stateId: number): VoxelShape | null;
}
```

### 3. DDA 邊界與 tie handling 不完整 — High

必須明確定義：

- 負方向整數邊界的起始 cell
- 同時穿越兩個或三個軸時的處理
- `tMaxX === tMaxY` 時避免漏格的規則

並加入整數邊界、edge 與 corner 穿越測試。

### 4. Palette 容量計算錯誤 — High

若預留 air state 後再加入 65536 個非 air state，總數會是 65537，超出 `Uint16Array` 的 index 範圍。

應限制：

```ts
palette.size <= 65536
```

超過限制時必須拋出明確錯誤，或改用更大的 index 格式。

### 5. 規格錯誤地假設沒有 raw voxel 存取 — High

目前仍有多個地方直接讀寫 raw voxel array。Palette 改造後，這些地方可能把 palette index 誤當成 global state ID。

必須列出並遷移所有 raw access，並明確定義：

- raw array 儲存 palette index 還是 global state ID
- 外部 API 接受哪一種 ID
- collision、mesher、undo、generator 是否必須透過 accessor

### 6. 非完整方塊缺少渲染資料路徑 — High

規格定義了 collision/outline shape，卻沒有完整定義 render shape。因此半磚、樓梯與植物可能仍被渲染成完整 cube。

必須補充：

- `renderShape(state)` 的資料模型
- 多個 box 如何產生 mesh
- 內部面如何消除
- stairs/slab 的 face mapping
- cross geometry 的實際實作

### 7. Compound collider API 未定義 — High

規格要求同一個 Static Body 包含 voxel collider 與多個 cuboid colliders，但沒有提供目前引擎可執行的 `NodePhysicsOptions` 結構。

必須先確認：

- compound body 的建立方式
- full/non-full collision 的分類
- 多 box shape 如何轉成 collider
- voxelSize、scale、translation 如何套用
- collider 更新如何與 chunk rebuild 整合

### 8. Neighbor update 的遞迴與 batching 不相容 — High

同步遞迴與 batch、drag、preset、undo/redo 及延遲 rebuild 尚未整合。

建議使用顯式 worklist：

```ts
const queue: VoxelCell[] = [];
const visited = new Set<string>();
```

統一 transaction 流程：

1. 收集原始編輯
2. 寫入 block state
3. 處理受影響鄰居
4. 收集 dirty chunks
5. 一次重建 mesh/collider
6. 建立 undo batch

### 9. 兩份文件的階段順序不一致 — Medium

兩份文件對 neighbor update 的階段順序及 queue/同步遞迴策略不一致，應建立唯一的 canonical phase plan。

建議順序：

1. Contract / compatibility migration
2. `VoxelShape`、`BlockType`、`BlockStateRegistry`
3. Palette 與 raw access migration
4. World voxel accessor
5. Shape-aware meshing
6. DDA raycast
7. Placement / build transaction
8. Neighbor worklist
9. Collision API spike
10. Collision implementation
11. Non-full block integration
12. Regression/performance tests

### 10. Serialization 與 undo/redo 相容性沒有規格 — High

尚未定義 registry version、stable block state identity、舊資料轉換、palette serialization、unknown block、undo replay 及 neighbor update。

Undo 不應直接寫入 palette index array，而應透過統一的 world mutation API 回放 global state。

### 11. Placement 的反例敘述自相矛盾 — Medium

文件中的半磚與樓梯案例實際計算出正確 placement cell，卻被描述成錯誤案例。

應改為說明舊方法依賴浮點 hit location，而新方法使用 DDA 確定的 `cell + normal`，或改用真正會失敗的反例。

## 可接受的假設

以下假設可以接受，但必須寫入正式規格：

1. `Float32Array` 儲存 `[0,1]` voxel-local 座標。
2. `distance` 只作資訊用途。
3. `placementCell = hit.cell + hit.normal`。
4. `breakCell = hit.cell`。
5. air 使用 state ID 0。
6. chunk 尺寸固定為 `16×256×16`。
7. 不修改 engine 原始碼，透過 remove/re-register workaround 更新 collider。

## 最終建議

先不要直接開始第 1 階段。完成 Phase 0 的規格修訂與 API/相容性 Spike，特別是：

1. world/chunk voxel accessor
2. DDA 座標與邊界語意
3. Palette migration
4. shape-aware rendering
5. compound collider API
6. serialization/undo contract

Phase 0 完成並更新兩份規格後，再從 `VoxelShape` + `blockShapes` 開始實作。
