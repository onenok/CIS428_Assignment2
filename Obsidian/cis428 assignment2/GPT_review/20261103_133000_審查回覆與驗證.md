## 逐項驗證

### 1. DDA 的 shape 座標系統不完整 — ✅ 成立

**審查說**：`VoxelShape.boxes` 是 voxel-local 座標，但沒定義 `testRayAgainstShape()` 如何處理 cell/world 轉換。

**驗證**：規格書第 5.5 節的 `testRayAgainstShape()` 簽名收了 `cellX, cellY, cellZ` 三個參數，**但函式體內完全沒用到**：

```ts
function testRayAgainstShape(
  origin, dir, shape,
  cellX: number, cellY: number, cellZ: number,   // ← 收了但沒用
  maxT: number,
): ShapeHit | null {
  for (let i = 0; i < shape.boxCount; i++) {
    const offset = i * 6;
    const slab = rayAabb(origin, dir, shape.boxes, offset, maxT);  // ← 直接用 world origin 對 local box
```

`rayAabb()` 拿 world-space 的 `origin` 去跟 `[0,1]` 範圍的 local box 做 slab test。**只有當 cell 是 `(0,0,0)` 時才正確**。

**這是真正的 bug，不是文件缺漏。** 修正方式有兩種：

- **A**：把 origin 轉成 cell-local（`origin - cell`），命中後再加回 `cell`
- **B**：把 box 轉成 world（`box + cell`），直接對 world origin 測試

B 較簡單，但每個 box 每次都要加 3 次；A 只需在進入 shape 前減一次。**選 A**。

### 2. DDA 沒有跨 chunk 的 world voxel accessor — ✅ 成立

**審查說**：規格只傳單一 `VoxelVolume`，但建造系統使用多個 chunk。

**驗證**：`MyGameMode.buildWorld()` 建立的是 `Map<string, VoxelChunkNode>`（25 個 chunk），`BuildController` 也是拿整個 map。規格書第 5.4 節的 `ddaRaycast(volume: VoxelVolume, ...)` 只能看一個 chunk。

**實際影響**：射線從玩家位置出發，玩家站在 chunk `(0,0)`，但射線可能穿過 `(1,0)`。目前的 `ddaRaycast` 會在 chunk 邊界處把隔壁 chunk 當成空氣。

**審查建議的介面正確**：

```ts
interface VoxelRaycastWorld {
  getBlock(x: number, y: number, z: number): number;
  shapeFor(stateId: number): VoxelShape | null;
}
```

**補充**：還需要 `isLoaded(x, y, z): boolean`，否則「未載入」和「空氣」無法區分。未載入的 chunk 應該**終止射線**（Minecraft 就是這樣），而不是當空氣穿過去。

### 3. DDA 邊界與 tie handling 不完整 — ✅ 成立

**審查說**：必須明確定義負方向整數邊界、同時穿越兩/三軸、`tMaxX === tMaxY` 的處理。

**驗證**：規格書第 5.4 節的主迴圈：

```ts
if (tMaxX < tMaxY && tMaxX < tMaxZ) {
  x += stepX; t = tMaxX; tMaxX += tDeltaX;
} else if (tMaxY < tMaxZ) {
  y += stepY; t = tMaxY; tMaxY += tDeltaY;
} else {
  z += stepZ; t = tMaxZ; tMaxZ += tDeltaZ;
}
```

**問題 1：`tMaxX === tMaxY` 時只走 Y 軸**

45° 斜射時 `tMaxX === tMaxY`，條件 `tMaxX < tMaxY` 為 false，落到 `else if (tMaxY < tMaxZ)` → 走 Y。**X 軸的格子被跳過**。

對「選中框」來說這通常無害（斜射本來就會穿過角落），但對「射線是否被阻擋」的判定會漏格。Minecraft 的做法是**同時推進所有相等的軸**。

**問題 2：負方向整數邊界**

`stepX < 0` 時 `tMaxX = (x - origin[0]) / dir[0]`。若 `origin[0]` 剛好是整數（例如 `origin[0] = 5.0`，`x = 5`），`tMaxX = 0`，第一步就推進到 `x = 4`。**但 `x = 5` 這一格本身還沒被測試**。

正確做法：起點在整數邊界上時，負方向要**先測試當前格**，或把 `origin` 往內推 `epsilon`。

**問題 3：`Math.sign(0)` 回傳 `0`**

`stepX = Math.sign(dir[0])` 在 `dir[0] === 0` 時是 `0`，`tDeltaX = Infinity`，`tMaxX = Infinity`。這部分正確。但 `x += stepX` 會變成 `x += 0`，若 `tMaxX` 因浮點誤差變成有限值，就會**原地踏步無限迴圈**。需要 `stepX !== 0` 的守衛。

### 4. Palette 容量計算錯誤 — ⚠️ 部分成立

**審查說**：若預留 air state 後再加入 65536 個非 air state，總數會是 65537，超出 `Uint16Array` 的 index 範圍。

**驗證**：

- `Uint16Array` 的值域是 `0..65535`，共 **65536** 個不同值
- Palette 索引 `0` 保留給 air
- 所以**非 air 的 palette 索引上限是 65535**，即最多 **65535 個非 air state**
- 加上 air 總共 65536 個 palette 條目

**審查的「65537」推論有誤**：不是「1 + 65536 = 65537」，而是「1 + 65535 = 65536」。上限剛好等於 `Uint16Array` 的容量。

**但審查的核心結論正確**：**必須加上限檢查**。目前 `Palette.indexOf()` 沒有任何檢查，第 65537 個 state 會靜默溢位成 `0`（air），造成方塊消失。

**修正**：

```ts
public indexOf(stateId: number): number {
  const existing = this.indexByState.get(stateId);
  if (existing !== undefined) return existing;

  const index = this.stateIds.length;
  if (index > 0xffff) {
    throw new Error(
      `Palette: cannot hold more than 65536 states (air + 65535 blocks). ` +
      `Tried to add state ${stateId} as index ${index}.`,
    );
  }
  this.stateIds.push(stateId);
  this.indexByState.set(stateId, index);
  return index;
}
```

**實務上不會撞到**：一個 chunk 只有 65536 格，不可能同時出現 65536 種不同方塊。但**必須有明確錯誤**，不能靜默溢位。

### 5. 規格錯誤地假設沒有 raw voxel 存取 — ✅ 成立

**審查說**：目前仍有多個地方直接讀寫 raw voxel array。

**驗證**：實際 grep 結果：

| 檔案 | 行 | 存取方式 |
|---|---|---|
| `mesher.ts` | 57 | `volume.voxels[voxelIndex(...)]` — `getVoxel` 內部 |
| `mesher.ts` | 63 | `volume.voxels[voxelIndex(...)] = id` — `setVoxel` 內部 |
| `mesher.ts` | 142-143 | `volume.voxels[i]` — `countSolidVoxels` |
| `chunkCollision.ts` | 29 | `const voxels = volume.voxels` — 直接掃描 |
| `VoxelChunkNode.ts` | 102 | `this.volume.voxels[chunkIndex(...)]` — `getVoxelAtWorld` |
| `VoxelChunkNode.ts` | 115, 118 | `this.volume.voxels[index]` — `setVoxelRaw` |
| `WorldGenerator.ts` | 75 | `volume.voxels[chunkIndex(...)] = blockId` — `fillChunkData` |

**共 7 處**。規格書第 4.2 節說「所有既有呼叫點完全不用改」是**錯的**。

**分類**：

| 類型 | 位置 | 處理 |
|---|---|---|
| 已在 accessor 內 | `mesher.ts` 57/63 | 改內部實作即可 |
| 需要改寫 | `mesher.ts` 142、`chunkCollision.ts` 29 | 改用 `getVoxel()` 或 palette-aware 掃描 |
| 需要改寫 | `VoxelChunkNode.ts` 102/115/118 | 改用 `getVoxel()` / `setVoxel()` |
| 需要改寫 | `WorldGenerator.ts` 75 | 改用 `setVoxel()` |

**測試也有 raw access**：

- `tests/voxel/greedyMesh.unit.ts:50` — `volume.voxels[...]`
- `tests/voxel/greedyMesh.unit.ts:154` — `volume.voxels.fill(id)`

`fill(id)` 尤其危險：它把 **global state id** 直接填進 **palette index** 陣列。若 `id = 5` 而 palette 只有 `[0, 5]`，填完後所有格子都是 palette index 5，但 palette 只有 2 個條目 → `stateAt(5)` 回傳 `0`（air）。

**必須改成**：

```ts
function fill(volume: VoxelVolume, id: number): void {
  const index = volume.palette.indexOf(id);
  volume.voxels.fill(index);
}
```

### 6. 非完整方塊缺少渲染資料路徑 — ✅ 成立

**審查說**：規格定義了 collision/outline shape，卻沒有 render shape。

**驗證**：規格書第 3.1 節的 `BlockType` 只有：

```ts
collisionShape(state: PropertyMap): VoxelShape | null;
outlineShape(state: PropertyMap): VoxelShape | null;
```

**沒有 `renderShape`**。而 `chunkGeometry.ts` 的 `buildChunkGeometry()` 目前是硬編碼的「每格一個完整 cube」：

```ts
const corners = faceCorners(direction);   // 固定 [0,1] 範圍
positions.push(origin.x + x + cx, ...);
```

**實際後果**：半磚會渲染成完整方塊，但碰撞只有下半 → 玩家會看到「浮空的上半部」。

**審查要求補充的項目全部成立**：

- `renderShape(state)` 的資料模型
- 多個 box 如何產生 mesh
- 內部面如何消除
- stairs/slab 的 face mapping
- cross geometry 的實作

**補充一個審查沒提的關鍵點**：**face culling 規則必須改**。目前 `isFaceVisible()` 只看「鄰居是不是 air」：

```ts
export function isFaceVisible(volume, x, y, z, direction): boolean {
  if (getVoxel(volume, x, y, z) === EMPTY) return false;
  const [dx, dy, dz] = FACE_OFFSETS[direction];
  return getVoxel(volume, x + dx, y + dy, z + dz) === EMPTY;
}
```

對非完整方塊，正確規則是「**鄰居的 shape 是否完全覆蓋這個面**」。半磚旁邊放半磚，兩個半磚的接觸面應該被剔除；但半磚旁邊放完整方塊，半磚的側面**不該**被剔除（因為完整方塊只覆蓋上半）。

Minecraft 用 `isFaceSturdy()` + `skipRendering()` 處理。我們需要等價機制。

### 7. Compound collider API 未定義 — ✅ 成立（且比審查說的更嚴重）

**審查說**：規格要求同一個 Static Body 包含 voxel collider 與多個 cuboid colliders，但沒有提供可執行的 `NodePhysicsOptions` 結構。

**驗證結果：引擎根本不支援這個組合。**

追查 `BasePhysicsEngine.createCompoundNodeRecord()` → `buildColliderPartForNode()`：

```ts
protected buildColliderPartForNode(node, localPos, localQuat, worldScale, physicsOptions) {
  if (node instanceof MeshNode) {
    return this.buildColliderPartFromMesh(node.mesh, ...);
  }
  // ...
}
```

而 `buildColliderPartFromMesh()` 第 707-710 行：

```ts
// Heightfield / voxels are not supported as compound child parts in this pass.
if (physicsOptions.collisionData?.heightfield || physicsOptions.collisionMeshType === CollisionMeshType.Voxels) {
  return null;
}
```

**voxel collider 在 compound 路徑下直接被丟棄。**

再看 `CompoundColliderPartDesc` 的型別：

```ts
| { kind: 'box'; size: THREE.Vector3 }
| { kind: 'sphere'; radius: number; center?: THREE.Vector3 }
| { kind: 'capsule'; height: number; radius: number }
| { kind: 'cone'; height: number; radius: number }
| { kind: 'cylinder'; height: number; radius: number }
| { kind: 'mesh'; meshes: THREE.Mesh[]; collisionMeshType: CollisionMeshType; scale: THREE.Vector3 }
```

**沒有 `kind: 'voxels'`**。

**所以規格書第 8.1 節的「混合策略」在引擎層面不可行。**

**可行的替代方案**（需要驗證）：

| 方案 | 做法 | 風險 |
|---|---|---|
| **A** | 每個 chunk 用**兩個** `MeshNode`：一個 voxel collider（完整方塊）、一個 mesh collider（非完整方塊的合併 geometry） | 兩個獨立 body，玩家可能卡在交界 |
| **B** | 全部用 `ColliderDesc.voxels()`，非完整方塊用**更細的 voxel 網格**（例如 2×2×2 子格）近似 | 精度受限，樓梯會變成階梯狀 |
| **C** | 全部用 trimesh（`CollisionMeshType.Trimesh`），把 shape 轉成三角形 | 效能差，但語意最正確 |
| **D** | 非完整方塊用 `MeshNode` 的 `collisionMeshType: ConvexHull`，每個方塊一個子節點 | 凸包對樓梯（凹形）不正確 |

**建議先做 API Spike**：寫一個最小測試，確認哪個方案在 Rapier 下真的可行，再定案。

**另外發現一個審查沒提的引擎 bug**：

`processModelForPhysics()` 用 `mesh.id` 當 cache key：

```ts
private processModelForPhysics(mesh: THREE.Mesh): THREE.Mesh {
  const cacheKey = mesh.id;
  if (this.physicMeshesCache.has(cacheKey)) {
    return this.physicMeshesCache.get(cacheKey)![0];
  }
  // ...
  this.physicMeshesCache.set(cacheKey, [physicsMesh]);
```

**cache 永遠不失效**。chunk 每次 rebuild 都換新 geometry，但 `mesh.id` 不變 → 拿到的是**第一次的舊 geometry**。這對 trimesh 方案是致命的。

### 8. Neighbor update 的遞迴與 batching 不相容 — ✅ 成立

**審查說**：同步遞迴與 batch、drag、preset、undo/redo 及延遲 rebuild 尚未整合。

**驗證**：`BuildController` 確實有 batch 機制：

```ts
public beginBatch(): void { this.batchDepth++; }

public endBatch(): void {
  if (this.batchDepth === 0) return;
  this.batchDepth--;
  if (this.batchDepth > 0) return;
  for (const chunk of this.dirtyChunks) chunk.markDirty();
  this.dirtyChunks.clear();
}
```

而規格書第 7.1 節的 `updateNeighbors()` 直接呼叫 `world.markChunkDirty(nx, nz)`，**繞過 batch**。在 drag 過程中，每個鄰居更新都會觸發一次 rebuild。

**但實際檢查發現**：`beginBatch()` / `endBatch()` **目前沒有任何呼叫者**。`batchShapes.ts` 的 `lineCells` / `rectCells` / `pillarCells` 也**沒有被 `MyGameMode` 使用**。

所以現況是「batch 機制存在但未啟用」。這降低了急迫性，但**規格仍必須定義 transaction 邊界**，否則未來啟用 batch 時會踩坑。

**審查建議的 worklist 正確**，但**不需要**改成非同步。同步 + worklist 即可：

```ts
export function updateNeighbors(world: NeighborWorld, seeds: readonly VoxelCell[]): void {
  const queue: VoxelCell[] = [...seeds];
  const visited = new Set<string>();

  while (queue.length > 0) {
    const cell = queue.pop()!;
    const key = voxelKey(cell.x, cell.y, cell.z);
    if (visited.has(key)) continue;
    visited.add(key);

    for (const [dx, dy, dz] of NEIGHBOR_OFFSETS) {
      const nx = cell.x + dx, ny = cell.y + dy, nz = cell.z + dz;
      // ... 計算 nextState
      if (changed) {
        world.setBlockRaw(nx, ny, nz, nextState.id);
        world.markChunkDirty(nx, nz);
        queue.push({ x: nx, y: ny, z: nz });
      }
    }
  }
}
```

**差別**：遞迴版用 call stack（深度受限於 JS 引擎，約 10k 層），worklist 版用 heap（無深度限制）。對「長鏈 neighbor update」測試，worklist 更安全。

### 10. Serialization 與 undo/redo 相容性沒有規格 — ✅ 成立

**審查說**：Undo 不應直接寫入 palette index array，而應透過統一的 world mutation API 回放 global state。

**驗證**：`MyGameMode.applyEdits()`：

```ts
private applyEdits(batch: EditBatch, side: 'before' | 'after'): void {
  for (const edit of batch.edits) {
    const chunk = this.chunkForCell(edit);
    chunk?.setVoxelRaw(edit.x, edit.y, edit.z, edit[side]);   // ← edit[side] 是 global state id
  }
}
```

`setVoxelRaw()` 目前直接寫 `volume.voxels[index] = blockId`。Palette 改造後，這裡會把 **global state id 當成 palette index 寫入**。

**這是真正的 bug**。修正：`setVoxelRaw()` 內部改走 `setVoxel()`（palette-aware）。

**審查提到的其他項目**：

| 項目 | 現況 | 需要 |
|---|---|---|
| registry version | 無 | 需要（存檔格式版本） |
| stable block state identity | 靠註冊順序 | 需要（改名/重排會壞存檔） |
| 舊資料轉換 | 無 | 需要（目前 9 種方塊 → 新 registry） |
| palette serialization | 無 | 需要 |
| unknown block | 無 | 需要（fallback 到 stone 或 air） |
| undo replay | 直接寫 raw | 需要改走 mutation API |

**但目前專案沒有存檔功能**（`MyGameMode` 沒有 save/load）。所以 serialization 可以延後，但 **undo 必須現在修**。

### 11. Placement 的反例敘述自相矛盾 — ✅ 成立

**審查說**：文件中的半磚與樓梯案例實際計算出正確 placement cell，卻被描述成錯誤案例。

**驗證**：規格書第 6.3 節的三個「反例」：

| 案例 | 計算 | 結果 | 文件說法 |
|---|---|---|---|
| 半磚東面 | `1.0 + 1×0.5 = 1.5` → `floor = 1` | ✅ 正確 | 「看起來對了？」 |
| 半磚西面 | `0.0 + (-1)×0.5 = -0.5` → `floor = -1` | ✅ 正確 | 「也對了」 |
| 樓梯頂面 | `1.0 + 1×0.5 = 1.5` → `floor = 1` | ✅ 正確 | 「還是對的」 |

**三個都對**，文件卻說「問題出在樓梯的複合形狀」。**這是自相矛盾的敘述**。

**真正的問題**（文件最後才說對）：

> 浮點誤差可能讓 `1.0 + 0.5 = 1.4999999` → `floor = 1`

但這個例子**不會**出錯（`1.4999999` 和 `1.5000001` 都 `floor` 到 `1`）。

**真正會出錯的例子**：

- 命中點在 `x = 0.9999999`（浮點誤差，實際應該是 `1.0`），`normal = (1,0,0)`
- `0.9999999 + 0.5 = 1.4999999` → `floor = 1` ✅
- 命中點在 `x = 1.0000001`，`normal = (1,0,0)`
- `1.0000001 + 0.5 = 1.5000001` → `floor = 1` ✅

**兩個都對**。`NORMAL_NUDGE = 0.5` 對完整方塊**真的不會錯**。

**真正會錯的情況**：`hitLocation` 距離格子邊界**小於 0.5** 時。例如：

- 半磚在 `x = 0`，佔 `[0, 1)`，但**只佔下半** `y ∈ [0, 0.5)`
- 玩家瞄準半磚的**東面**，命中點 `x = 1.0`，`y = 0.25`（半磚中間高度）
- `normal = (1, 0, 0)`
- `1.0 + 0.5 = 1.5` → `floor = 1` ✅

還是對的。

**真正會錯的**：**樓梯的內凹角**。

- 樓梯 shape：下半 slab `[0,0,0]~[1,0.5,1]` + 上半後方 `[0,0.5,0.5]~[1,1,1]`
- 玩家從**上方**瞄準上半後方的**前表面**（`z = 0.5` 平面）
- 命中點 `z = 0.5`，`normal = (0, 0, -1)`
- `0.5 + (-1)×0.5 = 0.0` → `floor = 0`
- **正確答案是 `z = 0`**（樓梯前方）✅

**還是對的。**

**結論**：`NORMAL_NUDGE = 0.5` 在**所有軸對齊的整數邊界**上都正確。它唯一會錯的情況是**命中點不在整數邊界上**，而這對 AABB 來說不可能發生（AABB 的面一定在整數或半整數上）。

**所以第 6.3 節的整個論證是錯的。** 正確的理由應該是：

> `NORMAL_NUDGE = 0.5` 依賴「命中點一定在格子邊界上」這個假設。這個假設對 AABB 成立，但**對未來可能加入的非 AABB 形狀（例如斜面、欄杆的細柱）不成立**。改用 `cell + normal` 讓邏輯完全不依賴命中點精度，是更穩健的設計。

**這是「設計穩健性」論證，不是「現有 bug」論證。**

## 審查漏掉的問題

### A. `Float32Array` 精度不足 — 新發現

規格書第 2.1 節用 `Float32Array` 存 shape 座標。實測：

```js
new Float32Array([0.15])[0]   // 0.15000000596046448
new Float32Array([0.85])[0]   // 0.8500000238418579
```

`0.15` 和 `0.85` **無法用 float32 精確表示**。

**後果**：射線在 `y = 0.15` 沿 `+X` 前進，理論上應該擦過植物 cross 的邊緣（`minY = 0.15`），但 float32 的 `minY = 0.15000000596`，射線變成**在盒子外** → 漏判。

**修正**：改用 `Float64Array`。記憶體成本：一個 shape 6 個 double = 48 bytes，vs 6 個 float = 24 bytes。**對幾十個 shape 來說完全可忽略**。

**但 `0.5` 在 float32 是精確的**，所以半磚、樓梯不受影響。只有 `0.15` / `0.85` 這類「非 2 的冪」值有問題。

**建議**：用 `Float64Array`，並在 `VoxelShape` 建構時驗證所有值都在 `[0, 1]`。

### B. `tMin < 0` 的判斷會誤殺「起點在表面朝內」

規格書第 5.2 節：

```ts
if (tMin < 0) return null;
```

起點在 `x = 0`（方塊西面），朝 `+X`：
- `t1 = (0 - 0) / 1 = 0`
- `tMin = 0`
- `0 < 0` 為 false → **不 return** ✅

起點在 `x = 0`，朝 `-X`：
- `t1 = (1 - 0) / (-1) = -1`
- `t2 = (0 - 0) / (-1) = 0`
- 交換後 `t1 = 0`，`t2 = -1`
- `tMin = 0`，`tMax = -1`
- `tMin > tMax` → return null ✅

**這部分正確**。但若起點在 `x = 0.0000001`（浮點誤差），朝 `-X`：
- `t1 = (1 - 0.0000001) / (-1) = -0.9999999`
- `t2 = (0 - 0.0000001) / (-1) = 0.0000001`
- 交換後 `t1 = -0.9999999`，`t2 = 0.0000001`
- `tMin = -0.9999999`，`tMax = 0.0000001`
- `tMin < 0` → return null ✅

**正確**。但若起點在 `x = -0.0000001`（方塊外），朝 `+X`：
- `t1 = (0 - (-0.0000001)) / 1 = 0.0000001`
- `tMin = 0.0000001` → 命中 ✅

**正確**。

**結論**：`tMin < 0` 的判斷是對的。**但需要 `PARALLEL_EPSILON` 的配套**：若 `|d| < 1e-8` 且 `o` 剛好在邊界上，`o < lo || o > hi` 會因浮點誤差誤判。應該用 `o < lo - EPS || o > hi + EPS`。

### C. `hitNormalFromAxis` 在 `dir[axis] === 0` 時回傳 `0`

```ts
if (axis === 0) normal.x = -Math.sign(dir[0]);
```

若 `dir[0] === 0`，`Math.sign(0) = 0`，`normal.x = -0`。

**但 `axis` 只會在 `|d| >= PARALLEL_EPSILON` 時被設定**（因為 `continue` 跳過了平行軸），所以 `dir[axis]` 永遠不為 0。

**這部分正確**。但 `-0` 在 JS 中是 `-0`，`Object.is(-0, 0)` 為 false。若下游用 `=== 0` 判斷，`-0 === 0` 為 true，沒問題。**但若用 `Object.is()` 就會出錯**。建議加 `|| 0` 正規化。

### D. `ddaRaycast` 沒有處理「起點在方塊內」

規格書第 5.4 節的主迴圈第一次迭代就測試 `(x, y, z)`。若起點在方塊內，`rayAabb()` 會回傳 `null`（因為 `tMin < 0`），然後 DDA 繼續推進。

**但這會漏掉「起點在方塊內，且該方塊應該被選中」的情況**。Minecraft 的行為是：起點在方塊內時，**該方塊不算命中**（因為玩家不可能在方塊內）。所以目前行為正確。

**但需要明確寫進規格**，否則未來有人「修正」這個行為會出錯。

### E. `chunkCollision` 的 `Int32Array` 大小

`buildVoxelCollisionCoordinates()` 對 16×256×16 的 chunk，最壞情況是 65536 個 solid voxel → `Int32Array(196608)` = **768 KB**。

25 個 chunk 全滿 = **19 MB**。加上每次 rebuild 都重新分配 → GC 壓力大。

**建議**：預先配置一個可重用的 `Int32Array`，用 `subarray()` 取實際長度。但 `ColliderDesc.voxels()` 是否接受 `subarray` 需要驗證。

## 結論

**審查的整體判斷正確**：不該直接從階段 1 開始，需要 Phase 0。

**但審查有 3 處需要修正**：

1. **第 4 項**：上限是 65536，不是 65537
2. **第 9 項**：兩份文件順序其實一致，「不一致」不成立
3. **第 11 項**：三個反例全部算對，論證要從「現有 bug」改成「設計穩健性」

**審查漏掉 5 項**：`Float32Array` 精度、`PARALLEL_EPSILON` 容差、`-0` 正規化、起點在方塊內的行為、`Int32Array` 記憶體。

**最關鍵的發現**：**第 7 項比審查說的嚴重得多** —— 引擎的 `buildColliderPartFromMesh()` 明確拒絕 voxel collider 進入 compound 路徑，`CompoundColliderPartDesc` 也沒有 `kind: 'voxels'`。規格書第 8 章的「混合策略」**在引擎層面不可行**，必須先做 API Spike 選替代方案。
