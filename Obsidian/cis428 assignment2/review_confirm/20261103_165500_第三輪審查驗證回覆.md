## 逐項驗證

### 1. `updateNeighbors()` 不重算 seed 本身 — ✅ 成立（🔴 High）

**審查說法**：`updateNeighbors()` 只處理 seed 的六個鄰居，沒有重新計算 seed 本身。

**實測**（Node.js，完全複製規格書 7.1 的實作）：

```js
// 孤立 seed (0,0,0)，沒有鄰居
updateNeighbors(world2, [{x:0,y:0,z:0}]);
// => computeState called on []
// => seed itself recomputed? false
```

**確認**：`computeState()` 對 seed 的呼叫次數是 **0**。

**為什麼這是 bug**：

放置樓梯時，`place()` 寫入的是「預設 state」（`facing=north`）。正確的 `facing` 必須由 `computeState()` 依鄰居推導。但 `updateNeighbors(seeds=[新格子])` 只會檢查新格子的**鄰居**，不會檢查新格子本身。

**後果**：
- 新放的樓梯永遠是 `facing=north`，不管玩家從哪個方向放
- 新放的柵欄永遠不連接
- undo/redo 還原的樓梯 state 可能是錯的

**修正**：把 seed 本身也放進 worklist 的處理範圍。

```ts
export function updateNeighbors(
  world: NeighborWorld,
  seeds: readonly VoxelCell[],
): void {
  const queue: VoxelCell[] = [...seeds];
  const inQueue = new Set<string>();
  for (const seed of seeds) {
    inQueue.add(voxelKey(seed.x, seed.y, seed.z));
  }

  let iterations = 0;
  const MAX_ITERATIONS = 100_000;

  while (queue.length > 0) {
    if (++iterations > MAX_ITERATIONS) {
      throw new Error(`updateNeighbors: did not converge after ${MAX_ITERATIONS} iterations.`);
    }

    const cell = queue.shift()!;
    inQueue.delete(voxelKey(cell.x, cell.y, cell.z));

    // Recompute the cell itself first, then its neighbours. A freshly placed
    // stair keeps its default `facing` unless it is recomputed here.
    recomputeCell(world, cell.x, cell.y, cell.z, inQueue, queue);

    for (const [dx, dy, dz] of NEIGHBOR_OFFSETS) {
      recomputeCell(world, cell.x + dx, cell.y + dy, cell.z + dz, inQueue, queue);
    }
  }
}

function recomputeCell(
  world: NeighborWorld,
  x: number,
  y: number,
  z: number,
  inQueue: Set<string>,
  queue: VoxelCell[],
): void {
  const stateId = world.getBlock(x, y, z);
  if (stateId === 0) return;

  const state = world.stateFor(stateId);
  if (!state || !state.type.dependsOnNeighbors) return;

  const next = state.type.computeState?.(world, x, y, z);
  if (!next) return;

  const nextState = world.findState(state.type.id, next);
  if (!nextState || nextState.id === stateId) return;

  world.setBlockRaw(x, y, z, nextState.id);
  world.markChunkDirty(x, z);

  const key = voxelKey(x, y, z);
  if (!inQueue.has(key)) {
    inQueue.add(key);
    queue.push({ x, y, z });
  }
}
```

**驗收**：
- 在空地放一個樓梯 → `facing` 依玩家朝向決定，不是永遠 `north`
- 在樓梯旁放第二個樓梯 → 兩者的 `shape` 都正確
- 孤立 seed 的 `computeState` 呼叫次數 = 1（不是 0）

### 2. Registry 持久化契約不完整 — ✅ 成立（🟠 High）

**審查說法**：只有 `key` 與 `findByKey()`，缺少 save schema、registry version、key canonicalization、unknown-block fallback、version migration、載入錯誤策略。

**實際檢查**（grep 全文）：

```
registryVersion  → 0 筆
SerializedChunk  → 0 筆
migration        → 0 筆
unknown          → 0 筆
missing          → 0 筆
```

**確認**：完全沒有。

**缺少的六項**：

| 項目 | 現況 | 風險 |
|---|---|---|
| Save schema | 無定義 | 不知道存檔長什麼樣 |
| `registryVersion` | 無 | 無法判斷存檔是否相容 |
| Key canonicalization | 只有 `stateKey()` 排序 key，未定義「`facing=north` 與 `facing=NORTH` 是否等價」 | 大小寫/順序不一致會讀不到 |
| Unknown block fallback | 無 | 舊存檔遇到新方塊 → 崩潰或靜默變 air |
| Version migration | 無 | 改方塊定義後舊存檔全毀 |
| 載入錯誤策略 | 無 | 單一壞方塊讓整個存檔讀不進來 |

**修正**：定義完整存檔契約。

```ts
/** On-disk chunk format. Never stores runtime ids. */
export interface SerializedChunk {
  /** Bumped whenever the block registry changes incompatibly. */
  readonly registryVersion: number;
  /** Persistent state keys, index = palette index. */
  readonly palette: readonly string[];
  /** Palette indices, one per voxel. */
  readonly voxels: readonly number[];
}

/** Bumped manually whenever a block type is renamed or removed. */
export const REGISTRY_VERSION = 1;

/** Shown when a save references a block this build does not know. */
export const MISSING_BLOCK_KEY = 'minecraft:missing';
```

**載入流程**：

```
1. 讀 registryVersion
2. 若 > REGISTRY_VERSION → 拒絕載入（存檔來自更新的版本）
3. 若 < REGISTRY_VERSION → 執行 migration 鏈
4. 對 palette 的每個 key：
   a. findByKey(key) 命中 → 用該 state
   b. 未命中 → 用 MISSING_BLOCK_KEY（紫黑格），並記錄警告
5. 若 MISSING_BLOCK_KEY 本身未註冊 → 拋錯（這是程式錯誤）
```

**為什麼用 `minecraft:missing` 而不是 air**：

| 選項 | 問題 |
|---|---|
| 拋錯 | 整個存檔讀不進來，玩家失去所有進度 |
| 靜默變 air | 玩家會發現方塊消失，但不知道為什麼 |
| **`minecraft:missing`** | ✅ 玩家看得到「這裡有東西壞了」，且存檔仍可載入 |

**Key canonicalization 規則**：

```ts
function stateKey(typeId: string, properties: PropertyMap): string {
  const parts = Object.keys(properties)
    .sort()
    .map((k) => `${k}=${properties[k]}`);
  return parts.length === 0 ? typeId : `${typeId}[${parts.join(',')}]`;
}
```

**必須明文規定**：
- `typeId` 全小寫、`namespace:path` 格式
- property key 全小寫
- property value 全小寫
- 空 `properties` 不產生 `[]`

### 4. `BlockType` API 定義不一致 — ✅ 成立（🟠 High）

**實際檢查**：

| 位置 | 定義 |
|---|---|
| 實作規格書 3.1（L259-272） | `id` / `properties` / `defaults` / `dependsOnNeighbors` / `collisionShape()` / `outlineShape()` |
| 實作規格書 3.5（L388-392） | `+ renderShape()` |
| 實作規格書 7.2（L1224-1228） | `+ computeState?()` |
| 重構設計 3.1（L101-104） | 只有 `properties` / `collisionShape()` / `outlineShape()`，且回傳 `Float32Array`（**已過期**） |

**確認**：三處定義不一致，且重構設計的版本還寫 `Float32Array`。

**修正**：合併為單一完整介面。

```ts
export interface BlockType {
  /** Namespaced id, e.g. `minecraft:oak_stairs`. Lowercase. */
  readonly id: string;

  /** Declared properties and their allowed values. Empty for blocks without variants. */
  readonly properties: BlockProperties;

  /** Default property values, used when a state is not specified. */
  readonly defaults: PropertyMap;

  /**
   * True when the shape depends on neighbouring blocks (stairs, fences, walls).
   *
   * When true, `computeState` MUST be provided. `BlockStateRegistry.register()`
   * throws otherwise — a missing implementation would silently leave every
   * placed block in its default state.
   */
  readonly dependsOnNeighbors: boolean;

  /** Physics shape for a state, or `null` when entities pass through. */
  collisionShape(state: PropertyMap): VoxelShape | null;

  /** Selection shape for a state, or `null` when the block cannot be targeted. */
  outlineShape(state: PropertyMap): VoxelShape | null;

  /** Geometry shape for a state, or `null` when the block is not rendered. */
  renderShape(state: PropertyMap): VoxelShape | null;

  /**
   * Recomputes properties from neighbours.
   *
   * Required when `dependsOnNeighbors` is true, ignored otherwise.
   * Returns `null` when the current state is already correct.
   */
  computeState?(world: NeighborWorld, x: number, y: number, z: number): PropertyMap | null;
}
```

**必填 vs 選填**：

| 欄位 | 必填 | 說明 |
|---|---|---|
| `id` | ✅ | |
| `properties` | ✅ | 無變體時給 `{}` |
| `defaults` | ✅ | 無變體時給 `{}` |
| `dependsOnNeighbors` | ✅ | |
| `collisionShape` | ✅ | 可回傳 `null` |
| `outlineShape` | ✅ | 可回傳 `null` |
| `renderShape` | ✅ | 可回傳 `null` |
| `computeState` | ⬜ | `dependsOnNeighbors === true` 時**必填** |

### 5. Multi-box 內部面與面積 union 未定義 — ✅ 成立（🟡 Medium）

**實際檢查**（實作規格書 L462）：

> **注意**：這個規則假設「一個 box 覆蓋整個面」。對樓梯的階梯面（只覆蓋半個面），需要更細的**面積覆蓋**計算。第一版可以先接受「不剔除」，只求視覺正確（多畫幾個面不會錯，只是浪費）。

**確認**：規格自己承認未定義。

**缺少的四項**：

| 項目 | 現況 |
|---|---|
| 同一 shape 內部面剔除 | 未定義（樓梯的兩個 box 接觸面會被畫出來） |
| 同面區間 union | 未定義（兩個 box 各覆蓋半個面時，鄰居是否算「完全覆蓋」） |
| 跨方塊部分遮蔽 | 未定義（半磚旁邊放半磚，下半側面是否剔除） |
| Cross geometry | 未定義（花草的兩片交叉面怎麼產生） |

**修正**：定義 `RenderType` 與第一版驗收範圍。

```ts
export type RenderType =
  | 'cube'    // One or more axis-aligned boxes. Internal faces culled.
  | 'cross'   // Two diagonal quads. No culling, no collision.
  | 'none';   // Not rendered.
```

**第一版的明確近似範圍**（必須寫進規格，不能只說「先接受」）：

| 情況 | 第一版行為 | 是否可接受 |
|---|---|---|
| 同一 shape 的兩個 box 接觸面 | **不剔除**（多畫 2 個面） | ✅ 視覺無差異（面重合） |
| 半磚旁邊放半磚 | **不剔除**（多畫 1 個面） | ✅ 視覺無差異（面重合） |
| 半磚旁邊放完整方塊 | **不剔除**（多畫 1 個面） | ✅ 視覺無差異（面重合） |
| 樓梯階梯面被鄰居部分覆蓋 | **不剔除** | ⚠️ 會有 z-fighting 風險 |
| Cross 方塊 | 不剔除 | ✅ 本來就不剔除 |

**關鍵洞察**：**「不剔除」在幾何上永遠不會錯，只會多畫面**。真正的風險是 **z-fighting**（兩個重合面深度相同，GPU 隨機選一個）。

**所以第一版的驗收標準應該是**：

- ✅ 所有方塊的**外觀正確**（沒有缺面）
- ✅ 沒有**可見的** z-fighting（重合面因為深度測試而穩定）
- ⬜ 面數不是最優（可接受）

**第二版才做**：
- 同一 shape 內部面剔除（省 2 面/box）
- 同面區間 union（省 1 面/半磚）

### 6. DDA tie policy 不完整 — ✅ 成立（🟡 Medium）

**審查說法**：corner/edge tie 時的 traversal 與 normal 優先序仍依實作迴圈順序間接決定，且 API 未限制最大射程。

**實測**（Node.js）：

```js
// 45 度斜射進方塊角落 (0,0)
const s = Math.SQRT1_2;
const o = [-1, -1, 0.5];
const d = [s, s, 0];

// slab 迴圈順序 X → Y → Z
rayAabb(o, d, [0,0,0], [1,1,1], 100);
// => { t: 1.414213562373095, axis: 0 }   ← X 軸
// => normal = [-1, 0, 0]

// slab 迴圈順序 Y → X → Z
rayAabbYFirst(o, d, [0,0,0], [1,1,1], 100);
// => { t: 1.414213562373095, axis: 1 }   ← Y 軸
// => 兩者一致? false
```

**確認**：`hitAxis` 完全由迴圈順序決定，不是幾何性質。

**後果**：玩家斜射方塊角落時，放置格可能是側面或頂面，取決於實作細節。這在 Minecraft 裡是**有明確定義**的（取決於射線方向與命中點）。

**修正**：定義正式的 tie policy。

```ts
/**
 * Tie-break order for corner and edge hits.
 *
 * When two or three axes are entered at the same distance, the axis with the
 * highest priority wins. Priority is Y > X > Z, matching Minecraft: a ray that
 * grazes a block's top edge should place on top, not on the side.
 */
const AXIS_PRIORITY: readonly number[] = [1, 0, 2];   // Y, X, Z

function rayAabb(
  origin: readonly [number, number, number],
  dir: readonly [number, number, number],
  boxes: Float64Array,
  offset: number,
  maxT: number,
): { t: number; axis: number } | null {
  let tMin = -Infinity;
  let tMax = maxT;
  let hitAxis = -1;
  let hitPriority = Infinity;

  for (const axis of AXIS_PRIORITY) {
    const o = origin[axis];
    const d = dir[axis];
    const lo = boxes[offset + axis];
    const hi = boxes[offset + axis + 3];

    if (Math.abs(d) < PARALLEL_EPSILON) {
      if (o < lo - PARALLEL_EPSILON || o > hi + PARALLEL_EPSILON) return null;
      continue;
    }

    let t1 = (lo - o) / d;
    let t2 = (hi - o) / d;
    if (t1 > t2) { const tmp = t1; t1 = t2; t2 = tmp; }

    if (t1 > tMin + TIE_EPSILON) {
      tMin = t1;
      hitAxis = axis;
      hitPriority = AXIS_PRIORITY.indexOf(axis);
    } else if (Math.abs(t1 - tMin) <= TIE_EPSILON) {
      // Tie: keep the higher-priority axis.
      const priority = AXIS_PRIORITY.indexOf(axis);
      if (priority < hitPriority) {
        hitAxis = axis;
        hitPriority = priority;
      }
    }

    if (t2 < tMax) tMax = t2;
    if (tMin > tMax) return null;
  }

  if (tMin < 0) return null;
  return { t: tMin, axis: hitAxis };
}
```

**最大射程上限**：

```ts
/** Hard cap on raycast distance. Prevents a misconfigured reach from
 *  scanning the whole world. */
export const MAX_RAYCAST_DISTANCE = 64;

if (maxT > MAX_RAYCAST_DISTANCE) {
  throw new RangeError(
    `ddaRaycast: maxDistance ${maxT} exceeds MAX_RAYCAST_DISTANCE (${MAX_RAYCAST_DISTANCE}).`,
  );
}
```

**為什麼是 64**：Minecraft 的 `reach` 是 4.5（生存）/ 5（創造），但射線可能從相機出發（相機在玩家眼睛位置），加上第三人稱偏移。64 是安全上限，遠超任何合理值。

**驗收**：
- 45° 斜射方塊角落 → `hitAxis` 永遠是 Y（不論迴圈順序）
- 45° 斜射方塊邊線（X-Y 邊）→ `hitAxis` 永遠是 Y
- `maxT = 100` → 拋 `RangeError`

### 7. 碰撞方案 A/B 命名相反 — ✅ 成立（🟡 Medium）

**實際對照**：

| 文件 | 方案 A | 方案 B |
|---|---|---|
| 重構設計 3.4（L202-247） | **子格細分** | **兩個 `MeshNode`** |
| 實作規格書 8.1（L1366-1367） | **兩個 `MeshNode`** | **子格細分** |

**確認**：完全相反。

**後果**：Spike 測試、記憶體評估、fallback 選擇全部會對錯方案。

**修正**：改用具體名稱，不用 A/B。

### 8. Collider lifecycle 契約缺失 — ✅ 成立（🟡 Medium）

**審查說法**：缺少 rebuild 後 postcondition、重複 rebuild 行為、失敗回復策略。

**實際檢查**（grep 全文）：

```
postcondition  → 0 筆
重複 rebuild   → 0 筆
失敗回復       → 0 筆
lifecycle      → 0 筆
```

**確認**：完全沒有。

**缺少的三項**：

| 項目 | 現況 | 風險 |
|---|---|---|
| rebuild 後 postcondition | 無 | 不知道「成功」長什麼樣 |
| 重複 rebuild 行為 | 無 | 連續編輯同一 chunk 可能洩漏 body |
| 失敗回復 | 無 | `removeNode()` 成功但 `addNode()` 失敗 → chunk 完全沒有碰撞 |

**修正**：定義唯一 API contract。

```ts
/**
 * Rebuilds the chunk's physics collider.
 *
 * Postcondition on success:
 *   - `physics.hasNode(voxelMesh)` is true
 *   - `physics.hasNode(meshMesh)` is true (DualMeshNode only)
 *   - The collider reflects the current voxel data
 *
 * Postcondition on failure:
 *   - The chunk has NO collider (entities fall through)
 *   - `this.collisionValid` is false
 *   - The error is logged once, not every frame
 *
 * Idempotent: calling twice in a row produces the same result as calling once.
 */
public rebuildCollision(): void {
  const physics = this.getPhysicsEngine();
  if (!physics) return;

  // Remove first: `overridePhysicsOptions()` does not unregister, so a stale
  // body would otherwise survive and keep the old collider.
  for (const mesh of this.collisionMeshes()) {
    if (physics.hasNode(mesh)) physics.removeNode(mesh);
  }

  try {
    for (const mesh of this.collisionMeshes()) {
      mesh.overridePhysicsOptions(buildChunkPhysicsOptions(this.volume));
      mesh.registerPhysicsBody();
    }
    this.collisionValid = true;
  } catch (error) {
    this.collisionValid = false;
    if (!this.collisionErrorLogged) {
      this.collisionErrorLogged = true;
      console.error(`VoxelChunkNode.rebuildCollision failed at ${this.chunkX},${this.chunkZ}:`, error);
    }
  }
}
```

**為什麼要 `collisionValid`**：讓 `MyGameMode` 能偵測「這個 chunk 沒有碰撞」，並在 UI 顯示警告，而不是讓玩家莫名其妙掉下去。

**驗收**：
- 編輯方塊 → collider 立即更新（射線命中新位置）
- 連續編輯 10 次 → body 數量不變（無洩漏）
- 故意讓 `buildChunkPhysicsOptions()` 拋錯 → `collisionValid === false`，只記錄一次

### 9. 細薄形狀無正式碰撞方案 — ✅ 成立（🟠 High）

**審查說法**：文件已指出 `SUBDIVISION=2` 對柵欄、火把不可靠，但尚未決定正式解法。

**實際檢查**：重構設計 3.4 與實作規格書 8.1 都寫「待 API Spike 決定」，且沒有 fallback 驗收標準。

**確認**：確實未定案。

**這是本輪最需要使用者決策的一項。**

**三個選項**：

| 選項 | 柵欄碰撞 | 記憶體 | 實作複雜度 |
|---|---|---|---|
| **`VoxelSubdivision`（`SUBDIVISION=8`）** | 精確（0.125） | 400 MB/chunk ❌ | 低 |
| **`DualMeshNode`** | 精確（cuboid） | 19 MB/chunk ✅ | 中（兩個 body） |
| **接受膨脹** | 0.5 寬（4 倍） | 6.3 MB/chunk | 低 |

**建議：`DualMeshNode`**，理由：

1. 記憶體可接受（19 MB vs 400 MB）
2. 細薄方塊精確（柵欄 0.125 就是 0.125）
3. 樓梯精確（不是階梯狀近似）
4. 交界通行已實測 ✅

**但必須先完成 Spike 驗證「編輯後 collider 更新」**（見第 8 項）。

**如果 `DualMeshNode` 的編輯後更新失敗**，fallback 順序：

1. `DualMeshNode` + 每次編輯重建兩個 body
2. `VoxelSubdivision(SUBDIVISION=4)` + 接受 0.25 最小厚度（柵欄膨脹 2 倍）
3. `VoxelSubdivision(SUBDIVISION=2)` + 接受 0.5 最小厚度（柵欄膨脹 4 倍）

**必須寫進規格的驗收標準**：

| 方塊 | 碰撞寬度 | 容許誤差 |
|---|---|---|
| 完整方塊 | 1.0 | 0 |
| 半磚 | 1.0 × 0.5 × 1.0 | 0 |
| 樓梯 | 精確階梯 | 0 |
| 柵欄 | 0.125 | ≤ 0.125 |
| 火把 | 0.125 | ≤ 0.125 |

**「≤ 0.125」的意思是**：如果方案只能做到 0.25，那就不合格。

### 11. `VoxelShape.boxes` 可被外部修改 — ✅ 成立（🟡 Medium）

**實測**（Node.js）：

```js
const s = new VoxelShape(new Float64Array([0,0,0,1,1,1]));
s.boxes[3] = 0.5;   // 外部直接改寫
// => 外部可修改? true
```

**`Object.freeze()` 對 TypedArray 無效**：

```js
Object.freeze(new Float64Array([0,0,0,1,1,1]));
// TypeError: Cannot freeze array buffer views with elements
```

**確認**：`readonly boxes` 只限制欄位重新指定，不限制元素修改。`Object.freeze()` 直接拋錯。

**後果**：任何拿到 `VoxelShape` 的程式碼都能改寫幾何資料，破壞：
- shape cache（`blockShapes.ts` 的共用實例）
- render（已產生的 mesh 與 shape 不一致）
- raycast（命中位置錯誤）
- collision（碰撞體與視覺不符）

**修正選項**：

| 方案 | 做法 | 成本 |
|---|---|---|
| **A. Defensive copy** | constructor 內 `this.boxes = boxes.slice()` | 每個 shape 多一份記憶體（幾十個 shape，可忽略） |
| **B. 私有欄位 + getter 回傳 copy** | `get boxes() { return this.#boxes.slice(); }` | 每次讀取都複製（hot loop 不可接受） |
| **C. 私有欄位 + 唯讀存取器** | `getBox(i, out)` 寫入呼叫端提供的陣列 | 改動所有呼叫點 |
| **D. 文件約定** | 只寫「不要修改」 | ❌ 不可靠 |

**建議：方案 A（defensive copy）**

```ts
export class VoxelShape {
  public readonly boxCount: number;
  private readonly data: Float64Array;

  public constructor(boxes: Float64Array) {
    // ... 驗證 ...
    // Defensive copy: `readonly` only prevents reassigning the field, not
    // mutating the elements. A shared shape instance is used by render,
    // raycast and collision, so one stray write would corrupt all three.
    this.data = boxes.slice();
    this.boxCount = this.data.length / 6;
  }

  /** Reads box `index` into `out` (6 values: minX, minY, minZ, maxX, maxY, maxZ). */
  public readBox(index: number, out: Float64Array): void {
    out.set(this.data.subarray(index * 6, index * 6 + 6));
  }

  /** Direct read-only view for hot loops. Callers MUST NOT write to it. */
  public get boxes(): Float64Array {
    return this.data;
  }
}
```

**為什麼保留 `boxes` getter**：hot loop（每幀、每個實體、每個鄰居方塊）不能每次複製。文件必須明文「**只讀**」，且 `readBox()` 提供安全路徑。

**更好的做法**：把 `boxes` 改成 `Readonly<Float64Array>` 型別（TS 沒有真正的唯讀 TypedArray，但可以用 `ReadonlyFloat64Array` 介面）。

```ts
/** Read-only view of a `Float64Array`. TypeScript has no built-in equivalent. */
export interface ReadonlyFloat64Array {
  readonly length: number;
  readonly [index: number]: number;
  subarray(begin: number, end?: number): ReadonlyFloat64Array;
}
```

**驗收**：
- `new VoxelShape(arr)` 後修改 `arr[0]` → shape 不受影響
- `shape.boxes[0] = 99` → TypeScript 編譯錯誤（用 `ReadonlyFloat64Array`）

### 12. `dependsOnNeighbors` 缺 `computeState` 靜默失效 — ✅ 成立（🟡 Medium）

**實測**（Node.js）：

```js
// 樓梯：dependsOnNeighbors = true，但忘記實作 computeState
states.set(1, { id:1, typeId:'stairs', dependsOnNeighbors:true, props:{facing:'north'} });

updateNeighbors(world, [{x:0,y:0,z:0}]);
// => { skipped: 1 }
// => 有拋錯嗎? NO
// => 有診斷嗎? NO
// => 方塊 state 保持過期值: true
```

**確認**：完全靜默。

**後果**：開發者忘記實作 `computeState()` 時，方塊永遠停在預設 state，且沒有任何提示。這在「新增 100 種方塊」的專案裡是必然會踩的坑。

**修正**：在註冊時驗證。

```ts
public register(type: BlockType): void {
  if (type.dependsOnNeighbors && typeof type.computeState !== 'function') {
    throw new Error(
      `BlockStateRegistry.register: "${type.id}" declares dependsOnNeighbors ` +
      `but does not implement computeState(). Every neighbour-dependent block ` +
      `would silently keep its default state.`,
    );
  }

  for (const properties of expandProperties(type)) {
    // ...
  }
}
```

**為什麼在註冊時拋錯而不是執行時**：

| 時機 | 優點 | 缺點 |
|---|---|---|
| **註冊時** | 啟動就失敗，開發者立刻知道 | 無 |
| 執行時 | — | 要等到玩家放那個方塊才會發現 |

**註冊時是唯一正確的時機**：這是靜態的介面契約違反，不是執行期資料問題。

**另外**：`updateNeighbors()` 內的 `state.type.computeState?.()` 可以改成 `state.type.computeState!()`，因為註冊時已驗證。
