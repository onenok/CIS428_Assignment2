# 方塊系統重構設計

> 建立日期：2026-11-03
> 狀態：**設計階段，尚未實作**
> 觸發原因：建造 raycast 打到玩家自己的碰撞膠囊（aim bug），追查後發現方塊系統需要整體重構

---

## 1. 問題陳述

### 1.1 直接觸發的 bug

建造模式的準星 raycast 會命中**玩家自己的碰撞膠囊**，導致：

- 準星看起來「瞄到空氣」
- 實際 `hitLocation` 在玩家腳邊
- `breakCell` 算出玩家站的那一格

**根因**：`MyGameMode.updateTargeting()` 的 `ignoredNodes` 只排除了 `selectionBox` 和 `placementPreview`，沒有排除玩家膠囊。

```ts
// src/game/MyGameMode.ts:783
const ignored: ENGINE.SceneNode[] = [];
if (selectionBox) ignored.push(selectionBox);
if (this.placementPreview) ignored.push(this.placementPreview);
const hit = build.raycastFromCamera(camera, SCREEN_CENTRE, ignored);
```

### 1.2 追查後發現的架構問題

| 概念 | 目前實作 | 問題 |
|---|---|---|
| **物理碰撞** | Rapier voxel collider（每 chunk 一個） | 只能表達「實心 / 空氣」 |
| **選中框** | 同一個 voxel collider 的 raycast 結果 | 無法獨立於物理碰撞 |
| **實體碰撞** | 玩家膠囊也在同一個物理世界 | raycast 會打到自己的膠囊 |

`isFaceVisible()` 用 `getVoxel(...) === EMPTY` 判斷 —— **渲染、碰撞、選中三者共用同一個「非空即實心」假設**。

### 1.3 未來擴充的阻礙

計畫加入 Minecraft 全部 vanilla 方塊，包含：

- **非完整方塊**：半磚、樓梯、柵欄、階梯
- **可穿透裝飾**：花草、藤蔓、紅石線、火把

目前的 `ColliderDesc.voxels()` **只接受整數網格座標**，無法表達 0.5 高的半磚。

## 2. Minecraft 的參考架構

### 2.1 三層分離

Minecraft 把「方塊」拆成三個獨立概念：

```
BlockType（方塊類型）
  minecraft:oak_stairs
  ├── getCollisionShape(state)  → 物理碰撞（實體能不能穿過）
  └── getOutlineShape(state)    → 選中框（準星能不能選中）

BlockState（方塊狀態）
  oak_stairs[facing=west,half=bottom,shape=straight] → 全域整數 id

Chunk（區塊儲存）
  PalettedContainer：palette（用到的 stateId）+ data（palette 索引）
```

### 2.2 預設關係

```java
// AbstractBlock 的預設實作
public VoxelShape getCollisionShape(...) {
    return state.getOutlineShape(...);   // 預設等於選中框
}
```

**一般情況：物理碰撞 = 選中框。**

**裝飾方塊：物理碰撞 = `VoxelShapes.empty()`，選中框保留。**

### 2.3 樓梯的狀態組合

```
facing:     4 (north / east / south / west)
half:       2 (top / bottom)
shape:      5 (straight / inner_left / inner_right / outer_left / outer_right)
waterlogged: 2
= 80 個狀態
```

`shape` 屬性**依賴鄰居**：放置或破壞周圍樓梯時，會觸發 `getStateForNeighborUpdate` 重新計算。

## 3. 目標架構

### 3.1 資料結構

```
BlockType（啟動時註冊）
  ├── id: string                                    ← "minecraft:oak_stairs"
  ├── properties: { facing: [...], half: [...] }
  ├── defaults: { facing: "north", half: "bottom" }
  ├── dependsOnNeighbors: boolean
  ├── collisionShape(state): VoxelShape | null      ← 預先計算並快取
  ├── outlineShape(state):   VoxelShape | null      ← 預先計算並快取
  ├── renderShape(state):    VoxelShape | null      ← 預先計算並快取
  └── computeState?(world, x, y, z): PropertyMap | null   ← dependsOnNeighbors 時必填

VoxelShape
  boxes: ReadonlyFloat64Array   ← [minX,minY,minZ,maxX,maxY,maxZ] × N
  occupancy: Uint8Array | null  ← L2/L3 剔除用，第一版不建

BlockStateRegistry
  stateId: number → { id, key, type, properties }
  key: string                   ← 持久化用，存檔只存這個
  啟動時展開所有組合，分配 0..N 的 int

Chunk（PalettedContainer）
  palette: number[]        ← 這個 chunk 用到的 stateId
  data:    Uint16Array     ← palette 索引（永遠 ≤ 65536）
```

**完整介面見 [方塊系統實作規格書.md](./方塊系統實作規格書.md) 第 3.1 節。** 本節只列結構，不重複定義。

**`VoxelShape` 不是 `Float32Array`**：`0.15` / `0.85` 在 float32 無法精確表示，射線擦邊會漏判。改用 `Float64Array`（見實作規格書 §2.1）。

**`key` 是持久化 identity**：`stateId` 依註冊順序分配，插入新方塊會讓後面全部位移。存檔只存 `key`（見實作規格書 §3.3）。

### 3.2 為什麼需要 Palette

`Uint16Array` 上限 65535。Minecraft 1.13+ 有 1000+ 種方塊，每種平均 10-20 個狀態：

- 樓梯一種就有 80 個狀態
- 全域 stateId 總數**遲早超過 65536**
- 超過時 `Uint16Array` **靜默截斷**（不報錯），方塊會變成錯誤的 id

**Palette 讓 id 空間無限**：`data` 存的是 palette 索引，而一個 chunk 最多 65536 格，不可能用到超過 65536 種不同狀態。

```ts
class ChunkSection {
  palette = [0];
  paletteIndex = new Map<number, number>();
  data = new Uint16Array(65536);   // 16×256×16，存 palette 索引

  setBlock(x: number, y: number, z: number, stateId: number): void {
    let idx = this.paletteIndex.get(stateId);
    if (idx === undefined) {
      idx = this.palette.length;
      this.palette.push(stateId);
      this.paletteIndex.set(stateId, idx);
    }
    this.data[x + y * 16 + z * 256] = idx;
  }
}
```

**已確認（第二輪 Q1/Q2）**：

- **不需要分層**。chunk 是 16×256×16 = 65536 格，`data` 是 `Uint16Array`（索引上限 65535），單一 palette 就夠用。
- **不需要重新打包**。每格固定 16 bit，palette 從 10 項長到 30000 項，`data` 的佈局完全不變。只有 bit 壓縮才需要重新打包。

> 唯一需要分層的情況：未來要做「局部 mesh 重建」或「區段 culling」時，切成 16 個 16×16×16 的 Section 會比較好管理。目前不需要。

### 3.3 VoxelShape 用 Float64Array

**不要用 `THREE.Box3[]`** —— 每次 `clone()` 都產生新物件，在 hot loop 裡會造成 GC 壓力。

```ts
// 每個 shape 是 [minX,minY,minZ,maxX,maxY,maxZ, ...] 的扁平陣列
const STAIRS_BOTTOM = new Float64Array([0, 0, 0, 1, 0.5, 1]);
const STAIRS_TOP    = new Float64Array([0, 0.5, 0.5, 1, 1, 1]);
```

**所有 shape 在啟動時預先計算並快取**，執行期只讀不寫。

```ts
export class VoxelShape {
  readonly boxCount: number;

  constructor(boxes: Float64Array) {
    if (boxes.length % 6 !== 0) {
      throw new Error(`VoxelShape: boxes.length (${boxes.length}) must be a multiple of 6.`);
    }
    for (let i = 0; i < boxes.length; i++) {
      const v = boxes[i];
      if (!Number.isFinite(v) || v < 0 || v > 1) {
        throw new Error(`VoxelShape: box coordinate ${i} (${v}) must be within [0, 1].`);
      }
    }
    this.boxes = boxes.slice();   // 防禦性複製
    this.boxCount = boxes.length / 6;   // 預先算好，不在 getter 裡做除法
  }

  readonly boxes: ReadonlyFloat64Array;
}
```

- **用 `Float64Array` 不用 `Float32Array`**（**Phase 0 修正**）：原本認為「方塊內座標嚴格在 `[0, 1]`，`Float32` 綽綽有餘」是**錯的**。實測 `new Float32Array([0.15])[0] === 0.15000000596046448`，`0.85` 同理。射線在 `y = 0.15` 沿 `+X` 前進時，理論上應該擦過植物 cross 的邊緣，但 float32 的 `minY` 稍大 → 射線變成在盒子外 → **漏判**。記憶體成本從 24 bytes/box 增加到 48 bytes/box，對幾十個 shape 完全可忽略。
- **`boxCount` 在 constructor 預先算好**：hot loop 裡每次 `length / 6` 都是浪費。
- **值域驗證**：`[0, 1]` 之外的值一定是打錯，早點拋錯比在 hot loop 裡產生詭異結果好。
- **防禦性複製 + `ReadonlyFloat64Array`**（**第三輪修正**）：`Float64Array` 是可變的，外部 `shape.boxes[3] = 0.5` 會直接改掉快取的 shape（實測會成功）。`Object.freeze()` 對 TypedArray 會拋 `TypeError: Cannot freeze array buffer views with elements`，所以改用「constructor 複製一份 + 回傳型別標成唯讀」。編譯期擋住寫入，執行期零成本，呼叫點不用改。

**L2/L3 剔除的預留位置**（使用者決策：第一版不做，但預留）：

`VoxelShape` 內部保留 `occupancy: Uint8Array | null` 與 `occupancyResolution`，預設 `null`。未來要啟用時：

1. `buildOccupancy(resolution)` 把 AABB 陣列光柵化成佔用格
2. `isOccupied(x, y, z)` 查詢單格
3. `coversFaceByOccupancy()` / `isFaceCoveredBySelf()` 從拋錯 stub 換成實作

**公開介面完全不變**，所以啟用 L2/L3 不需要改任何呼叫點。這與 Minecraft 的做法一致——Minecraft 的 `VoxelShape` 底層就是 `DiscreteVoxelShape`（`BitSet` 佔用格），AABB 是從格子合併出來的。我們保留 AABB 陣列是因為方塊種類少、樓梯/柵欄手寫容易、mesh 生成只要 ~20 行；`occupancy` 就是兩者之間的橋。

### 3.4 物理碰撞：`DualMeshNode`

**原方案的「voxel collider + cuboid collider 混合」在引擎層面不可行**（**Phase 0 修正**）。

追查 `BasePhysicsEngine.buildColliderPartFromMesh()` 第 707-710 行：

```ts
// Heightfield / voxels are not supported as compound child parts in this pass.
if (physicsOptions.collisionData?.heightfield || physicsOptions.collisionMeshType === CollisionMeshType.Voxels) {
  return null;
}
```

**voxel collider 在 compound 路徑下直接被丟棄。** 而且 `CompoundColliderPartDesc` 的型別根本沒有 `kind: 'voxels'`。

#### 候選方案（已定案）

**方案名稱不用 A/B**：兩份文件曾對 A/B 的定義相反，導致 Spike 對錯方案。改用具體名稱。

| 名稱 | 做法 | 判定 |
|---|---|---|
| **`DualMeshNode`** | 每個 chunk 用**兩個** `MeshNode`：一個 voxel collider（完整方塊）、一個 mesh collider（非完整方塊） | ✅ **採用** |
| **`VoxelSubdivision`** | 全部用 `ColliderDesc.voxels()`，非完整方塊用子格近似 | ❌ 記憶體爆炸 + 細薄方塊消失 |
| **`Trimesh`** | 全部用 `CollisionMeshType.Trimesh` | ❌ cache bug |
| **`ConvexHull`** | 非完整方塊用 `ConvexHull` | ❌ 樓梯凹形不正確 |

**已決定採用 `DualMeshNode`**（使用者 2026-11-03 確認）。

#### `VoxelSubdivision` 為什麼被否決

**問題 1：完整方塊只推單一子格會縮成 1/8 且錯位**

`(5,3,7)` 推 `(5,3,7)` 搭配 `voxelSize = 0.5` → 覆蓋 `[2.5,3)×[1.5,2)×[3.5,4)`，應該是 `[5,6)×[3,4)×[7,8)`。必須展開成 8 個子格 → 記憶體 8×。

**問題 2：`shapeContains(center)` 讓細薄形狀完全消失**

| 方塊 | `SUBDIVISION=2` 的子格數 |
|---|---|
| 柵欄（0.125 寬） | **0** |
| 火把（0.125 × 0.625 × 0.125） | **0** |

改用相交測試會「膨脹」成 0.5 寬（4 倍）。

**記憶體代價**：

| `SUBDIVISION` | 最小厚度 | 完整方塊子格 | 全滿 chunk | 25 個 chunk |
|---|---|---|---|---|
| 2 | 0.5 | 8 | 6.3 MB | 157 MB |
| 4 | 0.25 | 64 | 50 MB | 1.2 GB |
| 8 | 0.125（柵欄需要） | 512 | 400 MB | 10 GB |

**結論：無法同時滿足「完整方塊不膨脹」與「細薄方塊不消失」。**

#### `DualMeshNode` 的實測結果

| 測試 | 結果 |
|---|---|
| 兩個 voxel body 交界（x=4） | ✅ 正常通行（x 從 0.5 走到 8.6） |
| voxel body + mesh 半磚 | ❌ 卡住（原因是 autostep，不是交界，見 3.5） |

**優點**：完整方塊零浪費、細薄方塊精確（柵欄 0.125 就是 0.125）、樓梯精確
**缺點**：兩個 body 需要同步更新、每次編輯要重建 `meshMesh`

**實作要點**：

| 項目 | 做法 |
|---|---|
| 完整方塊 body | `ColliderDesc.voxels()`，`voxelSize = 1`，只推 `collisionShape` 是單一滿格 AABB 的方塊 |
| 非完整方塊 body | `CollisionMeshType.Trimesh`，由 `collisionShape` 的 AABB 陣列生成（每面 2 個三角形） |
| 兩個 body 的歸屬 | 同一個 `MeshNode` 的兩個 child，或兩個獨立 `MeshNode` 掛在同一個 parent 下 |
| 更新時機 | `BuildController.touch()` 觸發 chunk rebuild 時，兩個 body 一起重建 |
| 空集合 | 該類方塊數為 0 時不建立對應 body（避免空 collider） |

**完整實作規格見 [方塊系統實作規格書.md](./方塊系統實作規格書.md) 第 8 章。**

#### 為什麼不用 `Trimesh`

`BasePhysicsEngine.processModelForPhysics()` 用 `mesh.id` 當 cache key 且**永不失效**。chunk 每次 rebuild 都換新 geometry，但 `mesh.id` 不變 → 拿到第一次的舊 geometry → **編輯方塊後 collider 不會更新**。這是致命缺陷。

#### 為什麼不用 `ConvexHull`

凸包對樓梯（凹形）不正確。

#### 剩餘的 Spike 項目

**`DualMeshNode` 已選定，但 Spike 仍必須驗證「編輯後 collider 更新」。**

1. ✅ `DualMeshNode` 的兩個 body 交界通行（已初步驗證）
2. ⬜ **`DualMeshNode` 的編輯後 collider 更新**（最大風險）
3. ⬜ 每次編輯重建 `meshMesh` 的效能（100 次連續編輯）
4. ⬜ 手動 step-up 在 `DualMeshNode` 下能運作

**若第 2 項失敗**，fallback 順序：

1. `DualMeshNode` + 每次編輯重建兩個 body
2. `VoxelSubdivision(SUBDIVISION=4)` + 接受 0.25 最小厚度（柵欄膨脹 2 倍）
3. `VoxelSubdivision(SUBDIVISION=2)` + 接受 0.5 最小厚度（柵欄膨脹 4 倍）

### 3.5 實體移動：保留 Rapier，但 autostep 必須自寫

**不要自己寫 swept AABB。**

Rapier 的 `KinematicCharacterController` 已經處理：

- `maxSlopeClimbAngle`（斜坡攀爬）
- `snapToGroundDistance`（貼地）
- `slideEnabled`（滑牆）
- `applyImpulsesToDynamicBodies`（推動動態物件）

**但 `autoStepConfig` 實測完全失效**（第二輪審查發現）。

引擎設定 `maxHeight: CHARACTER_HEIGHT / 4 = 0.45`，但實測上限只有約 **0.12**：

| 台階高度 | 結果 |
|---|---|
| 0.05 / 0.10 | ✅ 跨越 |
| 0.15 / 0.20 / 0.25 / 0.30 / 0.40 / 0.45 / 0.50 | ❌ 全部卡住 |

**`maxHeight` 參數完全沒有作用**（測到 3.0 仍無效）。已排除 9 種變因：`minWidth`、`includeDynamicBodies`、`snapToGround`、`offset`、水平步長、膠囊半徑、台階寬度、重力、向上 bias。

**診斷輸出**：撞牆時碰撞法向量是 `(-1, 0, 0)`，角色完全靜止，autostep 從未觸發。

**這對 Minecraft 風格遊戲是致命的**：半磚（0.5）、樓梯（每階 0.5）玩家都走不上去。

**解法：手動 step-up**（已實測有效）

```ts
if (Math.abs(mv.x) < 0.001 && ctrl.computedGrounded()) {
  const lift = stepHeight + 0.02;
  charBody.setTranslation({ x: pos.x, y: pos.y + lift, z: pos.z }, true);
  world.step();
  ctrl.computeColliderMovement(charCol, { x: desiredX, y: 0, z: 0 });
  const mv2 = ctrl.computedMovement();
  if (Math.abs(mv2.x) > 0.001) {
    pos.y += lift;
    mv = mv2;
  } else {
    charBody.setTranslation(pos, true);
    world.step();
  }
}
```

**實測結果**：

| 台階高度 | 最終 `y` | 預期站立 `y` | 正確？ |
|---|---|---|---|
| 0.25 | 1.16 | 1.15 | ✅ |
| 0.50 | 1.41 | 1.40 | ✅ |

**注意事項**：

1. 必須檢查抬升後是否有空間（否則會穿牆）
2. 必須檢查抬升後是否真的能前進（否則會浮空）
3. 抬升失敗要復原
4. 每幀最多嘗試一次
5. `stepHeight` 應該從「前方方塊的碰撞形狀」推導，不是硬編碼 0.5

### 3.6 選中框：自寫 DDA voxel raycast

**不要用 `THREE.Raycaster.intersectObjects()`。**

理由：

1. chunk 是**合併的 BufferGeometry**，不是每格一個 Mesh → 只會回傳「打到哪個 chunk」
2. 會遍歷**所有** scene 物件（玩家模型、NPC、UI）→ 就是目前的 aim bug
3. **不認識 `outlineShape`** → 花草無法選中

**正確做法**：DDA voxel raycast（Amanatides & Woo 演算法）

```
沿著射線步進每個穿過的格子
  → 對命中的格子查 outlineShape
  → 對 shape 內的每個 AABB 做精確測試
  → 回傳第一個命中的 AABB
```

#### 3.6.1 回傳型別與 world accessor

```ts
export interface VoxelRaycastHit {
  readonly cell: { readonly x: number; readonly y: number; readonly z: number };
  readonly hitLocation: Vector3;
  readonly hitNormal: Vector3;
  /** 資訊性欄位：DDA 已保證第一個命中就是最近的，此值僅供 UI / 除錯使用。 */
  readonly distance: number;
}

/**
 * 世界層級的 voxel 存取介面（**Phase 0 新增**）。
 *
 * 建造系統橫跨多個 chunk，所以射線不能只吃單一 `VoxelVolume`。
 * `isLoaded` 與 `getBlock` 分開，因為「未載入」和「空氣」行為不同：
 * 射線離開已載入區域時應該**終止**，而不是當空氣穿過去。
 */
export interface VoxelRaycastWorld {
  getBlock(x: number, y: number, z: number): number;
  isLoaded(x: number, y: number, z: number): boolean;
  shapeFor(stateId: number): VoxelShape | null;
}
```

**已確認（第三輪補充、第四輪 Q19）**：`distance` 不參與邏輯判斷。

#### 3.6.2 Slab method（AABB 射線相交）

```ts
const PARALLEL_EPSILON = 1e-8;

function rayAabb(
  origin: readonly [number, number, number],
  dir: readonly [number, number, number],
  box: Float64Array,
  boxOffset: number,
  maxT: number,
): { t: number; axis: number } | null {
  let tMin = -Infinity;   // 不是 0
  let tMax = maxT;
  let hitAxis = -1;

  for (let axis = 0; axis < 3; axis++) {
    const d = dir[axis];
    const o = origin[axis];
    const lo = box[boxOffset + axis];
    const hi = box[boxOffset + axis + 3];

    if (Math.abs(d) < PARALLEL_EPSILON) {
      // 射線平行於此軸：起點必須落在 [lo, hi] 內。
      // 用 ±EPS 容差，避免射線剛好擦過邊界時被浮點誤差判成在外。
      if (o < lo - PARALLEL_EPSILON || o > hi + PARALLEL_EPSILON) return null;
      continue;
    }

    const invD = 1 / d;
    let t1 = (lo - o) * invD;
    let t2 = (hi - o) * invD;
    if (t1 > t2) { const tmp = t1; t1 = t2; t2 = tmp; }

    if (t1 > tMin) { tMin = t1; hitAxis = axis; }
    if (t2 < tMax) tMax = t2;
    if (tMin > tMax) return null;
  }

  if (tMin < 0) return null;   // 起點在 box 內，或貼著表面朝外
  return { t: tMin, axis: hitAxis };
}
```

**`origin` 與 `dir` 必須與 `box` 同一個座標空間**（**Phase 0 修正**）。`shape.boxes` 是 voxel-local 座標（`[0,1]` 範圍），所以呼叫前必須把射線轉成 cell-local：

```ts
const localOrigin = [origin[0] - cellX, origin[1] - cellY, origin[2] - cellZ];
```

原本的規格收了 `cellX/Y/Z` 參數卻沒用，只有 cell `(0,0,0)` 會正確。

**為什麼 `tMin` 必須是 `-Infinity`（第四輪 Q16）**：

| 情境 | `tMin = 0` | `tMin = -Infinity` |
|---|---|---|
| 起點在 box 外 | ✅ 命中 | ✅ 命中 |
| 起點在 box 表面，朝內 | ❌ **漏判** | ✅ 命中（`t = 0`） |
| 起點在 box 表面，朝外 | ✅ 跳過 | ✅ 跳過 |
| 起點在 box 內 | ✅ 跳過 | ✅ 跳過 |

用 `tMin = 0` 時，`t1 > tMin` 對 `t1 = 0` 為 false，`hitAxis` 不會被設定，導致貼著表面的命中被漏掉。

#### 3.6.3 法向量

```ts
function getHitNormal(
  dir: readonly [number, number, number],
  hitAxis: number,
): Vector3 {
  const normal = new Vector3(0, 0, 0);
// `|| 0` 把 -0 正規化成 0，避免下游 Object.is() 誤判。
  if (hitAxis === 0) normal.x = -Math.sign(dir[0]) || 0;
  else if (hitAxis === 1) normal.y = -Math.sign(dir[1]) || 0;
  else if (hitAxis === 2) normal.z = -Math.sign(dir[2]) || 0;
  return normal;
}
```

**為什麼不用「命中點貼近哪個面」（第三輪 Q10）**：

`else if` 鏈在斜射角落時只回傳第一個匹配的軸。例如射線 45° 斜射進方塊角落，命中點同時貼近 `maxX` 和 `maxY`，`else if` 會回傳 `+X`，但玩家可能想放頂面。

**`hitAxis` 由 slab method 記錄「最後進入的軸」**，這才是幾何上正確的碰撞面。

`Math.sign(0)` 不會發生（第四輪 Q17）：`hitAxis` 只在 `Math.abs(d) >= 1e-8` 時被設定。

#### 3.6.4 DDA 主迴圈

**完整實作見 [方塊系統實作規格書.md](./方塊系統實作規格書.md) 第 5.4 節。** 本節只說明設計決策，不重複程式碼。

**為什麼不重複程式碼**：兩份文件各自維護一份 DDA 實作，必然會再次不同步。第三輪審查就抓到本節的範例「簽名收 `volume`，內容用未宣告的 `world`」——連編譯都不會過。

**核心設計決策**：

| 決策 | 理由 |
|---|---|
| **三軸同時推進** | `tMaxX === tMaxY` 時只推進一<|place_holder_mm_span_0442|>會跳過對角格。用 `Math.min` + 三個獨立 `if` |
| **`TIE_EPSILON = 1e-9`** | `cos(π/4) ≠ sin(π/4)`（差 ~1e-16），45° 斜射永遠不會產生相等的 `tMax`。實測：不加 epsilon 時 200 步射線有 12 次非對角推進 |
| **`AXIS_PRIORITY = [1, 0, 2]`** | Corner tie 的法向量不能依迴圈順序決定。實測：X→Y→Z 給 `axis=0`，Y→X→Z 給 `axis=1`。固定 Y > X > Z（同 Minecraft） |
| **`MAX_RAYCAST_DISTANCE = 64`** | `maxT = Infinity` 會無限迴圈（實測 10 萬步未終止）。入口驗證拋 `RangeError` |
| **`VoxelRaycastWorld` 而非 `VoxelVolume`** | 射線要跨 chunk。`isLoaded()` 回傳 false 時終止射線，不當成空氣穿過去 |
| **起點在方塊內不算命中** | `rayAabb()` 回傳 `null`（`tMin < 0`），DDA 繼續推進。玩家不可能站在方塊內 |
| **迴圈條件 `t <= maxT`** | 確保 `t = reach` 的極限邊界被涵蓋 |

**`VoxelRaycastWorld` 介面**：

```ts
export interface VoxelRaycastWorld {
  /** False when the chunk at this cell is not loaded. Terminates the ray. */
  isLoaded(x: number, y: number, z: number): boolean;
  /** Global block-state id, or `EMPTY` for air. */
  getBlock(x: number, y: number, z: number): number;
  /** Collision shape for a state, or `null` when the block is pass-through. */
  shapeFor(stateId: number): VoxelShape | null;
}
```

**為什麼用 `shapeFor()` 而不是 `renderShapeFor()`**：射線要命中**碰撞形狀**，不是渲染形狀。花草的 collision 是 `null`（可穿透），所以射線會穿過去——這與 Minecraft 一致（花草不能被選中）。

#### 3.6.5 放置格與破壞格

```ts
// 放置：命中格 + 法向量
placementCell = {
  x: hit.cell.x + hit.hitNormal.x,
  y: hit.cell.y + hit.hitNormal.y,
  z: hit.cell.z + hit.hitNormal.z,
};

// 破壞：命中格本身
breakCell = hit.cell;
```

**這是本輪最重要的修正（第二輪 Q6/Q7）**。

現有的 `src/build/placement.ts` 用「命中點 + 法向量 × 0.5」再 floor：

```ts
const NORMAL_NUDGE = 0.5;
x: Math.floor(hit.hitLocation.x + hit.hitNormal.x * NORMAL_NUDGE)
```

**先說清楚：這個方法對完整方塊是正確的。** 逐項驗算：

| 情境 | `hitLocation` | `normal` | 計算 | 結果 | 正確？ |
|---|---|---|---|---|---|
| 完整方塊東面 | `x = 1.0` | `(1,0,0)` | `1.0 + 0.5 = 1.5` → `floor = 1` | `x = 1` | ✅ |
| 完整方塊西面 | `x = 0.0` | `(-1,0,0)` | `0.0 - 0.5 = -0.5` → `floor = -1` | `x = -1` | ✅ |
| 半磚東面 | `x = 1.0` | `(1,0,0)` | `1.0 + 0.5 = 1.5` → `floor = 1` | `x = 1` | ✅ |
| 樓梯內凹角 | `z = 0.5` | `(0,0,-1)` | `0.5 - 0.5 = 0.0` → `floor = 0` | `z = 0` | ✅ |

**全部正確。** 原因是 AABB 的面一定落在整數或半整數上，而 `±0.5` 的 nudge 剛好把命中點推到相鄰格子的內部。

**那為什麼還是要改？**

1. **依賴「命中點一定在格子邊界上」**：一旦引入非 AABB 幾何（斜面、欄杆細柱），命中點可能落在任意位置，`±0.5` 就不再保證正確。
2. **浮點誤差在邊界上會放大**：目前 `0.5` 遠大於誤差所以安全，但若未來為了支援更薄的方塊而調小 `NORMAL_NUDGE`，誤差就會跨過邊界。
3. **`cell + normal` 讓邏輯與精度完全解耦**：DDA 已經知道命中的是哪一格、哪個面，放置格就是「那一格往法向量方向推一格」，不需要任何浮點運算。

**結論**：`NORMAL_NUDGE = 0.5` **不是 bug**，是「碰巧正確但脆弱」的實作。改用 `cell + normal` 是**設計穩健性**的提升。

**連帶影響**：`HitLike` 必須增加 `cell` 欄位，`BuildController.raycastFromCamera()` 必須改回傳 `VoxelRaycastHit` 而非 `ENGINE.PhysicsQueryHit`。

#### 3.6.6 邊界檢查

`placementCell` 只做純數學位移，**不檢查世界邊界**。合法性由 `checkPlacement()` / `isWithinBuildBounds()` 統一處理（第四輪 Q18）。

### 3.7 鄰居更新

樓梯的 `shape` 依賴鄰居。放置或破壞樓梯時：

1. 寫入目標格
2. 檢查 6 個鄰居（**含跨 chunk**）
3. 對每個「依賴鄰居的方塊」重新計算 state
4. 標記受影響的 chunk 為 dirty

**跨 chunk 邊界**：chunk 是 16×256×16，樓梯在 `x=15` 時東邊鄰居在隔壁 chunk。必須自動計算隔壁 chunk 座標並標記 dirty。

**已確認（第二輪 Q8）**：**同步立即更新**，不用延遲佇列。單機 JS 環境沒有獨立的 game tick 迴圈，用佇列反而增加延遲。

**Phase 0 修正：改用 worklist 而非遞迴**

原本的遞迴版有兩個問題：

1. **深度受限於 JS call stack**（約 10k 層）。1000 個連續柵欄的長鏈更新會 stack overflow。
2. **繞過 `BuildController` 的 batch 機制**。`beginBatch()` / `endBatch()` 存在但目前無人呼叫，未來啟用時會踩坑。

```ts
function updateNeighbors(world: NeighborWorld, seeds: readonly VoxelCell[]): void {
  const queue: VoxelCell[] = [...seeds];
  const visited = new Set<string>();

  while (queue.length > 0) {
    const cell = queue.pop()!;
    const key = `${cell.x},${cell.y},${cell.z}`;
    if (visited.has(key)) continue;
    visited.add(key);

    for (const [dx, dy, dz] of NEIGHBOR_OFFSETS) {
      const nx = cell.x + dx, ny = cell.y + dy, nz = cell.z + dz;
      const stateId = world.getBlock(nx, ny, nz);
      if (stateId === 0) continue;

      const type = getBlockType(stateId);
      if (!type.dependsOnNeighbors) continue;

      const newState = type.computeState(world, nx, ny, nz);
      if (newState !== stateId) {
        world.setBlockRaw(nx, ny, nz, newState);
        world.markChunkDirty(nx, nz);
        queue.push({ x: nx, y: ny, z: nz });
      }
    }
  }
}
```

**`visited` 記錄的是「已處理的格子」**，不是「已更新的格子」—— 一個格子可能被多次要求更新，但只處理一次。

**`markChunkDirty()` 必須走 `BuildController.touch()`**，而不是直接 `chunk.markDirty()`，這樣 batch 才會生效。

## 6. 已知的引擎限制

### 6.1 `overridePhysicsOptions()` 的短路問題

`PrimitiveNode.doApplyPhysicsOptions()` 有 `JSON.stringify` 比較，但更關鍵的是 `registerPhysicsBody()`：

```ts
// .engine/src/nodes/PrimitiveNode.ts:276
if (physicsEngine.hasNode(this)) {
return;   // ← 直接返回，不重建 collider
}
```

`unregisterPhysicsBody()` 只呼叫 `removeNode()`。**`removeNode()` 確實會 `this.bodies.delete(node)`**（`BasePhysicsEngine.ts:1459-1474`），所以 `hasNode()` 之後回傳 `false`，`addNode()` 會重新執行。

**但真正的問題在 `overridePhysicsOptions()`**：它只更新 `this.physicsOptions`，**不呼叫 `unregisterPhysicsBody()`**。所以 `hasNode()` 仍是 `true` → `addNode()` 被跳過 → **collider 永遠是第一次建立的那個**。

**影響**：`VoxelChunkNode.rebuildCollision()` 呼叫 `overridePhysicsOptions()` 後，collider 不會更新。

**繞過方式**（階段 6 需要）：

```ts
private rebuildCollision(): void {
const mesh = this.meshNode;
if (!mesh) return;

const physics = this.getPhysicsEngine();
if (physics?.hasNode(mesh)) {
  physics.removeNode(mesh);
}
mesh.overridePhysicsOptions(buildChunkPhysicsOptions(this.volume));
}
```

`UIManager.ts:69` 無條件 `element.setStyle('pointerEvents', 'auto')`。除錯面板必須建立後再 `setStyle('pointerEvents', 'none')`。

### 6.3 `InputManager` 沒有 blur 監聽

註冊的事件只有 `keydown` / `keyup` / `mouse*` / `touch*` / `pointerlock*` / `gamepad*`，**沒有 `blur`**。held state 需要自己清。
