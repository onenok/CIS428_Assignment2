### 飛行實作

```typescript
export class FlyingMovementNode extends ENGINE.CharacterMovementNode {
  private isFlying = false;

  protected override performMovementStep(deltaTime: number): void {
    if (this.isFlying) {
      // 取消重力
      this.verticalVelocity = 0;
      if (input.isKeyDown(KeyBindings.flyUp)) this.verticalVelocity = 5;
      if (input.isKeyDown(KeyBindings.flyDown)) this.verticalVelocity = -5;
      // 水平移動照常
      // ...
    } else {
      super.performMovementStep(deltaTime);
    }
  }

  toggleFly(): void {
    this.isFlying = !this.isFlying;
    if (!this.isFlying) this.verticalVelocity = 0;
  }
}
```

**觸發**：雙擊空白鍵（`KeyBindings.toggleFly`）
**取消**：落地自動取消

## 第一人稱渲染機制（Minecraft 式）

### 為什麼不能直接把相機塞進頭部

如果相機放在角色頭部內部，會看到：

- 頭部方塊的內壁
- 肩膀、胸口的幾何
- 揮手時穿模

Minecraft 的解法是「**隱藏本體 + 獨立手臂**」。

### 四個步驟

| 步驟 | Minecraft 做法 | 引擎對應 | 狀態 |
|------|---------------|---------|------|
| 1. 相機定位 | 眼高偏移（成人 1.62 m） | `getInitialCameraPositions()` | 需設定 |
| 2. 隱藏本體 | 拒絕渲染自身模型 | `setHiddenInGame(true)` | ✅ 引擎內建 |
| 3. 獨立手臂 | 分離的手臂模型 + 矩陣動畫 | 自建 `MeshNode` 方塊手臂 | ✅ 已完成（方塊版） |
| 4. 近裁剪 + 深度 | 近裁剪面 + 最後繪製 | `CAMERA_NEAR` + 普通 depth test | ✅ 已完成 |

### 步驟 1：眼高

pawn 原點 = 碰撞箱**底面的中心**（Minecraft 慣例），所以 `y` 就是腳底：站在方塊上時 `y` 是整數。

| 項目 | 值 | 說明 |
|------|-----|------|
| `PLAYER_COLLISION_HEIGHT` | 1.8 | 我方常數（Minecraft 玩家碰撞箱高度） |
| 碰撞箱局部位置 | `y = +0.9` | collider 坐在原點**上方**：佔 `[0, 1.8]` |
| 碰撞箱底端 | `y = 0` | = pawn 原點 = 腳底 |
| 碰撞箱頂端 | `y = +1.8` | |
| 視覺模型 | `position.y = +0.9` | 人形模型以自身中心建模，往上抬半個身高讓腳踩在地面 |
| **眼睛高度** | **`y = 1.62`** | 從腳底量，1.8 的 90%（Minecraft 的 eye height） |

出生高度由 `MyGameMode.resolveSpawnGround()` 決定：`地面頂端 + 1`（往下掉 1 m 落地）。
不直接貼齊地面，因為 character controller 只用掃掠解重疊，貼齊等於一出生就重疊，會被卡住。

> 引擎預設的 `GameMode.resolveSpawnGround()` 假設「膠囊中心在原點」，回傳值要**減掉半個身高**才對得上本 pawn；而它偶爾會回報低一整格的地板，因此目前改用常數。詳見 [[ISSUE-009 玩家 y 必須是整數與碰撞箱原點]]。

### 碰撞箱：方形，不是膠囊

引擎 `CharacterPawn.createCollision()` 預設回傳 `CapsuleGeometry(0.45, 0.9)`（直徑 0.9、高 1.8 的圓柱加半球蓋）。voxel 關卡是整格思維，圓底會讓「站在方塊邊緣」「走進 1 格通道」變得不可靠，所以 `MyCharacterPawn` 覆寫它：

| 項目 | 值 | 說明 |
|------|-----|------|
| 形狀 | `BoxGeometry` | 引擎對非膠囊／圓錐／圓柱／球幾何會落到 `kind:"box"`，用 `boundingBox` 建 cuboid |
| `PLAYER_COLLISION_WIDTH` | 0.6 | Minecraft 玩家寬度與深度 |
| `PLAYER_COLLISION_HEIGHT` | 1.8 | Minecraft 玩家高度 |
| 節點類別 | `CollisionShapeNode` | 「幾何只用來定義 collider」，`beginPlay` 強制 `selfHidden = !isEditor` |
| 局部位置 | `(0, +0.9, 0)` | collider 佔 `[原點, 原點 + 1.8]`，原點 = 腳底 |
| `contributeToParentCollider` | `true` | collider 併入 pawn 的 kinematic body，而不是另外生一個 body |

實測（Play 模式，`queryPlay.raycast` 掃描高度）collider 佔 `y ∈ [11.0, 11.8]`，pawn `y = 11.0`，地面頂面 `11.0`：腳底與方塊頂面重合。

詳見 [[ISSUE-008 跳躍連跳與方形碰撞箱與奔跑]]、[[ISSUE-009 玩家 y 必須是整數與碰撞箱原點]]。

> 引擎的 debug 方塊 `RootMarker`（洋紅色，`PLAYER_ROOT_MARKER_SIZE = 0.2`）就畫在原點，也就是腳底，用來肉眼確認出生高度。

> ⚠️ 若設成 `0.15`（胸口偏下），相機會在模型內部，看到頭部內壁與身體背面。

### 步驟 2：隱藏本體（引擎內建）

`SceneNode.setHiddenInGame(true)` 的實作（`SceneNode.ts:892-905`）：

```typescript
private applyHiddenInGameRendering(hidden: boolean): void {
  const world = this.getWorld();
  if (!world || world.isEditorWorld) return;   // 編輯器裡仍可見
  const postProcess = world.gameLoop?.postProcessManager ?? null;
  if (hidden) {
    this.traverse(obj => obj.layers.disableAll());   // ① 相機層剔除
    postProcess?.addHiddenObjects(this);             // ② 加入隱藏清單
  } else {
    postProcess?.removeHiddenObjects(this);
    this.traverse(obj => obj.layers.enable(0));
  }
}
```

渲染管線在**主渲染 pass 前**把 `visible = false`，**渲染後立刻還原**（`WebGPUPipeline.js:427-434` / `574-577`）：

```javascript
// 渲染前
for (const obj of this.hiddenObjects) {
  if (obj.visible) {
    obj.visible = false;
    this.hiddenToRestore.push(obj);
  }
}
// ... 渲染 ...
finally {
  for (const obj of this.hiddenToRestore)
    obj.visible = true;   // 渲染後還原
}
```

**效果對照**

| 效果 | 是否保留 |
|------|---------|
| 主畫面看不到自己 | ✅ |
| **影子仍然存在** | ✅（shadow pass 在 `visible = false` 之前） |
| 動畫仍正常播放 | ✅（`AnimationStateMachineNode` 不受影響） |
| 碰撞仍正常 | ✅（`Collision` 是獨立節點，不受模型可見性影響） |
| 編輯器裡仍看得到 | ✅（`isEditorWorld` 直接 return） |

**為什麼不用 `visible = false`**

- `visible = false` 會連**影子**一起消失
- `setHiddenInGame` 只關相機層，`castShadow` 仍有效

**為什麼不覆寫 `setupVisualNode()` 回傳 `null`**

- `CharacterPawn.initialize()` 有檢查 `if (this.visualNode && !this.visualNode.parent) throw`
- 回傳 `null` 會讓 `animationNode` 找不到骨骼 → 動畫失效
- 保留節點、只關渲染最安全

### 步驟 3：獨立手臂（✅ 已實作，方塊手臂版）

引擎的 `ModelMeshNode` 載入的是**完整 glTF**，沒有「只取右臂」的選項。目前先用
`MeshNode` + `BoxGeometry` 做單一方塊手臂，掛在 `cameraPivot` 下：

| 項目 | 值 |
|------|-----|
| 尺寸 | `0.12 × 0.26 × 0.12`（`ARM_WIDTH` / `ARM_LENGTH`） |
| 相機空間位移 | `(0.24, -0.22, -0.36)`（右下前方） |
| 傾角 | `Euler(-0.5, -0.35, 0.12, 'YXZ')`，讓玩家看得到三個面 |
| 材質 | `MeshLambertMaterial`（受光才有立體感；`MeshBasicMaterial` 會變成純色貼紙） |
| 可見性 | 由 `hideBody()` 依 `bodyVisible` 反向控制（本體可見時手臂隱藏） |

> **⚠️ 深度坑（實測記錄）**
>
> `depthTest: false` + `renderOrder: 999` **在這個引擎行不通**。體素地形是獨立的 render pass，
> 不理會 `renderOrder`，會直接覆蓋手臂；而 `depthWrite: false` 也一樣會被地形蓋掉，
> 因為地形自己的 depth test 看不到手臂寫入的深度。
>
> 正確做法：**普通不透明材質、`depthTest` 與 `depthWrite` 都開**，靠「手臂比任何牆都近」取勝。
> 手臂在 0.36 m，玩家碰撞箱 0.6 寬，所以永遠不會被方塊擋住。

> **剩下的部分（Demo 後）**：換成 Steve 模型的真實右臂、走路正弦位移（view bobbing）。

### 步驟 3b：揮動動畫（✅ 已實作）

左右鍵都會觸發一次揮動，**打空也會揮**——那是「點擊被收到」唯一的視覺回饋，
否則非建造模式下點滑鼠完全沒反應。

| 項目 | 值 |
|------|-----|
| 樞紐點 | `FirstPersonArm`（**肘關節**）；手臂 mesh 是它的子節點，往 `y = +ARM_LENGTH/2` 伸出 |
| 時長 | `SWING_DURATION = 0.3` s（20 Hz 下的 6 ticks） |
| 推進 | `tickPrePhysics(deltaTime)` 累加 `deltaTime / SWING_DURATION` |
| 曲線 A | `swingArc = sin(√p · π)` — 1/4 處到峰值，之後緩慢回落（出手快、收回慢） |
| 曲線 B | `swingSnap = sin(p · π)` — 中點峰值，驅動側向甩動 |
| 位移 | 往相機 `+Z 0.03` m、往下 `−Y 0.02` m（肘幾乎不動，位移只是重量感） |
| 旋轉 | pitch **`−0.85`** rad、yaw `+0.25` rad、roll `+0.15` rad（皆乘上曲線值） |
| 連按 | 每次都 `swingProgress = 0` 重啟，像 Minecraft 一樣中斷上一次 |

**⚠️ 樞紐點與 pitch 正負號是這個功能的關鍵（兩個版本都寫錯過）**

第一版把樞紐點放在**手腕**、mesh 垂在 local `−Y`，結果 pivot 落在畫面中心那端、
「手」反而在畫面外——看起來像手肘在揮，而使用者要的正好相反：**手肘在畫面右下角外，
手是自由端**。所以 mesh 改成往 `+Y`（上＝遠離相機）延伸。

**正負號綁在 mesh 在 pivot 的哪一側，改邊就要翻號。** mesh 在 `+Y` 時：

- `Rx(+θ)` → 手朝相機，畫面上會看到手臂**背面**塞滿右下角（第一版就是這樣）
- `Rx(−θ)` → 手往前／往畫面外伸出，才是出拳感 ✅

**為什麼樞紐點不在 mesh 中心**

mesh 繞自己中心旋轉看起來像「一根漂浮的棍子在原地自轉」；掛在肘關節下才會畫出弧線。

**為什麼沒有 `partialTick` 插值**

引擎的 `TickManager` 每幀用真實 `deltaTime` 呼叫一次 `tickPrePhysics`，
不存在「固定 tick 邏輯 + 另一幀渲染」的雙時間軸。用 `deltaTime / 時長` 推進，
30 fps 與 300 fps 的揮動速度就一致，額外的 accumulator 只會多延遲一幀。

- 走路擺動（view bobbing）
- 長按連發：放置與破壞目前都是單次點擊，沒有「按住持續挖」的機制，所以也不需要重啟邏輯

## 雙視角切換

| 視角 | 相機 | Steve 是否可見 | 說明 |
|------|------|---------------|------|
| **第一人稱** | pawn 相機（`cameraPivot`） | ❌ 隱藏 | 建造、探索 |
| **上帝視角** | `ViewTargetCameraNode`（`TopDownMovementNode`） | ✅ **可見** | 建造（滑鼠選格） |

**切換方式**：`Tab`（`KeyBindings.toggleCameraMode`）

**上帝視角時的角色狀態**

- Steve **留在原地靜止**（不跟隨相機）
- 退出上帝視角後，Steve 在原位
- 上帝視角可看到 Steve 站在地上（Minecraft F5 第二人稱風格）

**實作要點**

- 上帝視角用 `world.pushViewTargetCamera(camera)` 推入相機堆疊
- 退出時 `world.removeViewTargetCamera(camera)`
- 切換時**不需要**改 `setHiddenInGame`（第一人稱的隱藏是常駐的，上帝視角用的是另一台相機）

> ⚠️ 但若第一人稱的隱藏是「常駐 `setHiddenInGame(true)`」，上帝視角也會看不到 Steve。
> 解法：切換到上帝視角時 `setHiddenInGame(false)`，切回第一人稱時 `setHiddenInGame(true)`。

### 移動方式：`NpcMovementNode`

**決定：用 `NpcMovementNode.setTargetPosition()`** —— 和一般角色移動一樣，只是沒有移動動畫。

```typescript
npcMovementNode.setTargetPosition(new THREE.Vector3(x, y, z), stopDistance);
```

引擎行為（已查證 `NpcMovementNode.ts`）：

| 行為 | 實作位置 | 說明 |
|---|---|---|
| 自動轉向 | `moveTowardPoint()` → `addLookRightInput(-yawDiff)` | 面向移動方向 |
| 自動前進 | `applyMovementInput()` → `addForwardInput(1.0)` | 轉向角度 < 45° 才前進 |
| 停止距離 | `hasReachedDestination()` → `currentStopDistance` | 不會撞到玩家 |
| 無 navmesh 時 | `calculateAndSetPathToPosition()` → `setPath([target], false)` | 直線移動，**不需要 navmesh** |
| 無動畫 | 沒有 `AnimationStateMachineNode` | 天然「沒有移動動畫」 |

**為什麼不用 `world.tweenManager`**：tween 補間不會轉向、不檢查碰撞（會穿牆）、沒有停止距離。

**為什麼不用 `AIController`**：`AIController` 是 Mover 系統（`MoverNode` + `MoverCharacterPawn`），本專案用舊系統（`CharacterPawn` + `CharacterMovementNode`）。

### 前置條件

`NpcMovementNode` 是 `CharacterMovementNode` 的子類，需掛在 `MovementPawn` 上。

| 織界者目前型別 | 需要做的事 |
|---|---|
| 純 `ModelMeshNode` | 改成 `MovementPawn` 或 `CharacterPawn`，把模型掛為子節點 |
| 已是 `MovementPawn` | 直接 `add(NpcMovementNode.create({...}))` |
